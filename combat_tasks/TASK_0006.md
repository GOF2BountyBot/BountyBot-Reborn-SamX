## Spec references

T6 honours fire-vs-apply separation: cluster's N sub-munitions are RECORDED in phase 3 (one fire event), APPLIED sequentially in phase 4; nuke's epicenter is SAMPLED in phase 3, damage APPLIED in phase 4.

## Deliverables

### D1. Shared subtype-dispatch infrastructure

**File:** `services/bot-core/src/services/combat_service.py` (alongside T5's primary firing path).

#### D1.1 — Per-secondary cooldown decrement

Mirror T5's primary path at Appendix B step 1. Each secondary weapon on a combatant carries its own `cooldown_remaining_ms` (init = 0 per §1), decremented by `TICK_MS` per tick, floored at 0, emits `cooldown_end` with `{system: weapon.name}` on the `> 0 → ≤ 0` transition. The cooldown semantics are identical to T5's; share a helper if natural but do NOT refactor T5's primary path to force-share (see Risks).

#### D1.2 — Range gate

Binary: `current_distance ≤ weapon.range_m`. Same convention as T5 (§2 / §6.1). Applies to every secondary subtype — rocket, missile, cluster-missile, nuke, shock-blast. A secondary outside its range does not fire, does not roll accuracy, does not sample nuke epicenter, does not emit `weapon_fire`; cooldown continues to tick.

#### D1.4 — Pure-EMP secondary path

Same shape as T5's pure-EMP primary handling — let the helper record a zero-amount `damage` event so the log surfaces that the weapon landed.

### D2. Rocket (§6.2 Rocket subsection)

**Subtype dispatch key:** `"rocket"`.

- **Accuracy:** linear curve per Appendix B "Rocket accuracy curve":
  ```
  accuracy = 0.05 + 0.55 × ((range_m − current_distance) / (range_m − MIN_DISTANCE_M))
           → clamp [0.05, 0.60]
  ```
  Read `range_m` from the weapon's seed, `MIN_DISTANCE_M` from `GameConstants`, `current_distance` from runtime state at fire time. NO §5 layered formula, NO thruster bonus, NO cloak override applies — this is a curve over distance only.
- **Roll RNG once** against the computed accuracy: `hit = rng.random() < accuracy`.
- **Single-target.** On hit, route `damage_per_shot` (seed value, integer) through T3's `_apply_damage(...)` helper — PvC DR + shield → armour → hull stacking is fully T3's responsibility.
- **`weapon_fire` event** with §12-conformant payload: `{slot: "secondary", subtype: "rocket", weapon: weapon.name, hit: bool, accuracy: float}`.
- **Cooldown:** reset to `loading_speed_ms` (seed value — PrimaryWeaponMod is primaries-only per §7.8 and does NOT apply to secondaries).

### D3. Missile (§6.2 Missile subsection)

**Subtype dispatch key:** `"missile"`.

- **Scanner-tier branch** driven by `combatant.scanner_tier.missile_tracking_active` (T4 D4 / D5):
  - **Tier A** (no combat scanner → `missile_tracking_active == False`): use the rocket curve (D2's formula). Same projectile, same `damage_per_shot`, same cooldown — only the accuracy track differs.
  - **Tier B / C** (`missile_tracking_active == True`): use `combatant.pilot_primary_acc` (already clamped per §5 by T4). No distance penalty. Pass through `weapon_accuracy(pilot_acc, weapon)` (T1 passthrough); do NOT re-clamp.
- **Roll RNG, single-target damage via T3 helper, cooldown reset to `loading_speed_ms`** — same shape as D2.
- **`weapon_fire` event (locked in §12 per-subtype table):** `{slot: "secondary", subtype: "missile", weapon, hit, accuracy, branch: "tier_a" | "tier_bc"}`. The `branch` field disambiguates which accuracy track was used.

### D4. Cluster missile (§6.2 Cluster missile subsection)

**Subtype dispatch key:** `"cluster-missile"`. Inherits the plain-Missile scanner-tier rule for whether tracking is active.

- **`burst_count: N`** read from `weapon.extra_atts["burst_count"]` generically — do NOT hard-code per weapon. Seed inventory: Shesha (3), Garuda-IV (4), Patala (5).
- **Accuracy snapshot semantics** (the §6.2-critical mechanic): the fire-time accuracy is captured **once** per cluster fire:
  - Tier B/C: snapshot = `combatant.pilot_primary_acc` at fire time (via `weapon_accuracy(...)` passthrough).
  - Tier A: snapshot = rocket-curve evaluated at fire-time `current_distance`.
  - **All N sub-munitions roll independently against the single snapshot.** Each sub-munition draws one `rng.random()` and compares to the snapshot. Distance change / module activation / scanner change between fire and resolution does NOT retroactively alter sub-munition rolls.
- **Damage application — per-sub-munition, sequential** (phase 4):
  - Each landing sub-munition deals `damage` (per-sub-munition value, NOT `burst_count × damage`) and walks shield → armour → hull *independently* via T3's helper.
  - Sub-munitions are applied **sequentially**: sub-munition 1 walks the stack to completion before sub-munition 2 is applied. Do NOT batch all N hits into a single pooled damage value before applying.
  - **Overkill allowed.** HP can go transiently negative within Appendix B step 4 — T3's helper already permits this. Step 4b clamps to 0; step 4a (T9) evaluates ES against cumulative end-of-phase hull.
- **Condensed log event** (the §6.2-explicit requirement): **ONE** `weapon_fire` event per cluster fire — NOT N rows. Payload:
  ```
  {slot: "secondary", subtype: "cluster-missile", weapon: weapon.name,
   fired: N, hits: K, damage_per_hit: <int>, total_damage: K × damage,
   branch: "tier_a" | "tier_bc", accuracy: <snapshot>}
  ```
  `total_damage` reports the weapon's *swung* output (max-possible across landed sub-munitions). The per-combatant `damage_dealt` rollup that T9 builds reads from absorbed-damage (post-clamp), not this field — don't conflate. Each sub-munition still produces a `damage` event (via T3's helper at phase 4); the condensation is for `weapon_fire` only.
- **EmergencySystem interaction:** ES evaluates against cumulative end-of-phase hull at step 4a (T9). A cluster going wildly past lethal triggers ES at most once. T6 just needs to not interfere with the cumulative-damage path — each sub-munition mutates `current_hull` via T3's helper; step 4a sees the final value. No special-casing in T6.
- **Cooldown:** reset to `loading_speed_ms` on fire (hit OR all-miss).

### D5. Nuke (§6.2 Nuke subsection)

**Subtype dispatch key:** `"nuke"`. Seed inventory: Liberator, Extinctor, Oppressor, Tormentor, Fireworks.

- **NO accuracy roll.** Bypasses §5 entirely — no cloak override consultation, no thruster/booster modifiers, no `weapon_accuracy(...)` call. `range_m` is the binary fire gate (consistent with primaries / §6.1). The implementer MUST NOT call `compute_pilot_accuracy(...)` or `weapon_accuracy(...)` in the nuke fire path.
- **Epicenter sampling** at phase 3 (fire eval): `epicenter = rng.uniform(MIN_DISTANCE_M, STARTING_DISTANCE_M)` — uses the **injected RNG from T4's seam**. Do NOT introduce a new RNG instance.
- **Both ships always take damage** (Appendix B "Nuke" block):
  - Firer at position 0 → `d_firer = epicenter`.
  - Opponent at `current_distance` → `d_opponent = |epicenter − current_distance|`.
- **Falloff** (inverse-square shape):
  ```
  effective_magnitude = magnitude_m × NUKE_MAGNITUDE_SCALE
  dmg(d) = damage × (1 − min(1, d / effective_magnitude))²
  ```
  `damage` and `magnitude_m` from seed. `NUKE_MAGNITUDE_SCALE` and `NUKE_FRIENDLY_FACTOR` from `GameConstants` (Appendix A).
- **Opponent damage** = `dmg(d_opponent)` — route through T3's damage helper (which integer-clamps and walks the stack).
- **Firer self-damage** = `dmg(d_firer) × NUKE_FRIENDLY_FACTOR` — also route through T3's damage helper. T3's helper applies PvC DR automatically when the recipient is the player; therefore **PvC DR applies to nuke self-damage** when the player fires (§3: "all incoming damage to the player, including own-nuke self-damage"). The implementer MUST NOT apply DR a second time inside the nuke path — double-discount bug.
- **Both damage applications happen in phase 4**, in canonical order: hits queued at phase 3 (one queue entry for opponent, one for self), drained at phase 4 with the standard C1-attacker → C2-target ordering for the opponent-damage entry, and the firer's own entry resolves against the firer in the same phase 4 (the attacker IS the target for self-damage — the queue entry just carries `target = firer`).
- **`steerable` flag IGNORED Phase-1.** Liberator's `steerable: true` is data-only fidelity; all 5 nukes behave identically except for `damage` and `magnitude_m`. Do not branch on it.
- **Cooldown:** standard `loading_speed_ms` decrement (no per-fight cap, no HP-threshold gating).
- **`weapon_fire` event** with payload:
  ```
  {slot: "secondary", subtype: "nuke", weapon: weapon.name,
   epicenter: <float>, d_firer: <float>, d_opponent: <float>,
   opponent_damage: <int>, self_damage: <int>}
  ```
  Per §12's per-subtype `weapon_fire` table, the nuke payload omits `hit`/`accuracy` (no roll) and carries `epicenter`, `opponent_damage`, `self_damage` as canonical fields. `d_firer` and `d_opponent` are additive debug fields permitted under Q9's lock (timeline readers can introspect AoE detail without re-deriving from `epicenter` + `current_distance`).

### D6. Shock-blast (§2 + §6.2 Shock-blast subsection)

**Subtype dispatch key:** `"shock-blast"` (seed: `misc.shock_blast.json`).

- **Pure distance reset utility.** Sets `current_distance := STARTING_DISTANCE_M` (default 5000 m). **100% guaranteed** — no accuracy roll, no RNG draw.
- **NO damage.** The seed file carries `damage: 140` / `emp_damage: 80` — **both IGNORED** per §6.2. Do not invoke T3's damage helper at all.
- **Cooldown:** standard `loading_speed_ms` decrement. No per-fight cap. No HP-threshold gating.
- **Module independence (§2 / §6.2):** active cloak / booster effects on either ship are **unaffected**. Cloak `duration_ms` keeps ticking; booster `effect_pct` keeps applying its accuracy debuff; thruster ramp recomputes against the new distance naturally. Module cooldowns and timers continue on their own clocks. T6 mutates only `current_distance` — no other state.
- **Events emitted:** TWO events per shock-blast fire:
  - `distance` event with `{from: <prev>, to: STARTING_DISTANCE_M, cause: "shock_blast"}`. Emitted at **phase 6** (locked) — Appendix B step 6 explicitly lists "shock-blast reset" alongside passive closure and booster push. The `weapon_fire` at phase 3 records the fire; the `distance` at phase 6 records the consequence. Reader correlates by `tick` value.
  - `weapon_fire` event with `{slot: "secondary", subtype: "shock-blast", weapon: weapon.name, hit: true, damage: 0}`. `hit=true` because the distance reset is 100% guaranteed; `damage: 0` is explicit (no shield/armour/hull mutation).

## Risk / notes

- **GPT-4o risk: 5 subtypes in one task (TODO.md line 128).** Recommended implementation order: **rocket → missile → cluster → nuke → shock-blast**. Simplest first; cluster + nuke are the trickiest. Each subtype gets its own bucket of tests landing alongside the implementation; don't try to land all 5 in one commit-pass before testing.
- **Cluster accuracy snapshot is the easiest-to-get-wrong mechanic in T6.** The §6.2 rule: capture accuracy ONCE at fire time, all N sub-munitions roll independently against the SAME value. Common bug: rolling each sub-munition against a freshly computed `pilot_primary_acc` (which would let mid-tick state changes leak into the sub-munition rolls). The snapshot must be a local variable captured at phase 3 fire time, not a per-sub-munition recompute.
- **Cluster `total_damage` semantic.** §6.2 defines it as `K × damage` (swung output, NOT post-clamp absorbed). T9 (summary builder) separately tracks per-combatant `damage_dealt` which is the absorbed (post-clamp) value. Don't conflate — `total_damage` in the `weapon_fire` payload is `K × damage`; the absorbed damage flows through T3's per-sub-munition `damage` events and rolls up at T9.
- **Nuke bypasses accuracy entirely (§6.2).** No cloak override, no thruster/booster modifiers, no `weapon_accuracy(...)` call. The implementer must NOT consult §5 layered accuracy for nuke firing — `range_m` is the only gate. A nuke against a cloaked opponent fires at full damage.
- **Nuke RNG seam.** `rng.uniform(MIN_DISTANCE_M, STARTING_DISTANCE_M)` uses the SAME injected RNG from T4. Don't construct a separate `random.Random()` for nuke sampling — that would break test determinism and is a regression from T4's seam contract.
- **Nuke self-damage path — DR applies via T3's helper, NOT a second time in T6.** §3 explicitly: "all incoming damage to the player, including own-nuke self-damage." T3's helper checks `state.is_player` and applies DR. T6 computes `raw_self_damage = dmg(d_firer) × NUKE_FRIENDLY_FACTOR` (pre-DR) and passes it to the helper. The helper applies DR. **Do not also multiply by `(1 − PVC_DAMAGE_REDUCTION)` in T6** — double-discount bug.
- **Shock-blast: seed `damage: 140` and `emp_damage: 80` are IGNORED (§6.2).** Easy regression: forgetting and accidentally invoking T3's damage helper. The shock-blast path must NOT call `_apply_damage(...)` at all. Verified by acceptance criterion (no HP delta).
- **Shock-blast does NOT affect module timers (§6.2 / §2).** Weapons and modules are independent subsystems. Cloak / booster duration timers continue running on their own clocks. Module cooldowns continue. Only `current_distance` resets. T6 mutates exactly one piece of state.
- **Sequential sub-munition damage application (§6.2 cluster).** Each sub-munition walks the stack BEFORE the next is applied. Sub-munition 1's damage drops shield to 0; sub-munition 2 starts at armour (because shield is now 0, T3's helper sees `current_shield == 0` and overflows into armour). Do NOT batch all N sub-munition damages into a single pool before applying — that would change the shield-soak math for clusters that span multiple layers.
- **Fire/apply separation (Appendix B).** Hits recorded in phase 3, applied in phase 4. Cluster: N sub-munitions all RECORDED at phase 3 (one fire event captured then), APPLIED sequentially at phase 4 (N damage applications). Nuke: epicenter sampled at phase 3, both damage applications enqueued; phase 4 drains the queue.
- **"Stay inside these files" guardrail (TODO.md line 128).** T6 is a cross-cutting risk task. The implementer should resist refactoring T5's primary firing path while adding the secondary path. Share helpers where natural (cooldown decrement, range gate, queue pattern) but do NOT churn T5's primary code. Each subtype's implementation should be additive.
- **Pure-EMP secondary handling matches T5's pure-EMP primary pattern.** Don't special-case-skip T3's damage helper — let it record a zero-amount `damage` event so the combat log shows the weapon landed. Same convention as T5's D5 pure-EMP primary handling.

The loadout builder may produce loadouts containing them. T6's dispatcher MUST handle them gracefully (noop or fire-but-noop per D1.3) — never crash on an unrecognised subtype.

The implementer must NOT read `effective_*` fields for secondaries — secondaries always read raw seed `damage` / `loading_speed_ms`. T5's `effective_primaries` runtime list is keyed to primaries only; T6 should not parallel-key secondaries to a mod (because there is no secondary mod in Phase-1).
