# T10 — Persistence + `fight_ships` cutover + Player stats + retire `SimpleTTKResolver`

## Spec references

- **§3** — PvC damage reduction (Keith T. Maxwell bonus). Default `PVC_DAMAGE_REDUCTION = 0.33` for PvC, `0.0` for PvP. Mandates retirement of `player_armour_buff` parameter and `BOUNTY_PVC_ARMOUR_BUFF_FACTOR` constant.
- **§12** — Combat log & results persistence: `combat_log` table semantics, `data` blob shape, `context` validation, `log_result` gating, `CombatService.fight_ships(...)` public API, callsite assignment table, retention, in-memory production → `FightResults` mapping, legacy `FightStats` wire-compat, "Why variance is dropped" rationale.
- **§13** — Player-profile stat promotion: 3 new counters (`total_fights`, `total_nukes_fired`, `total_module_activations`) gated by `log_result=True`; passive modules NOT counted.
- **Appendix A** — `COMBAT_LOG_RETENTION_HOURS = 72` (env `BOUNTYBOT_COMBAT_LOG_RETENTION_HOURS`).

## Entry conditions

- All of T1–T9 are merged.
- **T2** is the critical prereq (provides `combat_log` table, `Player` columns `total_fights` / `total_nukes_fired` / `total_module_activations`, and `CombatLogRepository` with `add()` + `delete_older_than(cutoff)`).
- **T9** is the immediate predecessor (provides `FightResults.combat_log` timeline + `FightResults.metadata` summary in the §12-mandated shape).
- T1's `GameConstants.COMBAT_LOG_RETENTION_HOURS` and `GameConstants.PVC_DAMAGE_REDUCTION` are landed and env-overridable.

## Deliverables

### (1) `CombatLogService.persist` (§12)

New service file: `services/bot-core/src/services/combat_log_service.py` (path matches the `combat_service.py` / `combat_preflight_service.py` sibling convention — flag if the developer subagent finds a different layout).

```python
class CombatLogService:
    async def persist(
        self,
        combat_meta: CombatMeta,          # see Risk note below
        fight_results: FightResults,
        context: str,
        session: AsyncSession,
    ) -> int:                              # returns combat_log.id
        ...
```

- **Projected columns** read from `fight_results.metadata` (already shaped per §12 by T9):
  `combatant1_name`, `combatant2_name`, `combatant1_user_id`, `combatant2_user_id`, `winner_name`, `is_stalemate`.
- **C1/C2 assignment rule** (§12): duels → challenger = C1, opponent = C2; PvC → player = C1, NPC = C2 with `combatant2_user_id = NULL`. T9 should already be emitting metadata in this assignment; persist trusts it.
- **`data` column** = the whole `fight_results.metadata` dict (which already contains `schema_version`, `summary`, `timeline`, `metadata` per §12 "data blob — internal schema").
- **`context` validation**: must be one of `{"duel", "bounty_pvc", "bounty_bonus"}`; reject anything else with `ValueError`.
- **NPC-vs-NPC invariant** (§12): assert at least one of `combatant{1,2}_user_id` is non-NULL. T2's repository should already enforce this — confirm during implementation; if not, raise here.
- **Returns** the new row's `id` for the caller to put on `FightResults.combat_log_id`.

Write via `CombatLogRepository.add()` (T2). All writes wrapped in `try/except` with `await session.rollback()` per the standard repo pattern.

### (3) `fight_ships(...)` signature cutover (§12)

In `services/bot-core/src/services/combat_service.py`:

```python
async def fight_ships(
    self,
    loadout1: ShipLoadout,
    loadout2: ShipLoadout,
    *,
    context: str | None = None,
    log_result: bool = True,
    pvc_damage_reduction: float = 0.0,
    guild_config: GuildConfig | None = None,
) -> FightResults
```

(Method is currently synchronous — promote to `async` if persistence + Player stat updates need a session. Confirm against T9's output shape; if T9 already routes through `await`, this is trivial.)

**Boundary validation** (raise immediately):
- `log_result=True ∧ context is None` → `ValueError`.

**`log_result=True` path** — after the tick resolver returns `FightResults`:
1. Persist via `CombatLogService.persist(...)` with caller's `context`.
2. Apply §13 Player stat increments for each HUMAN combatant (skip the NPC side — `combatant{1,2}_user_id IS NULL`).
3. Populate `FightResults.combat_log_id` from persist's return value.

**`log_result=False` path**:
- Run sim, return `FightResults` only. **No DB writes, no Player mutations, `FightResults.combat_log_id = None`.**
- Used exclusively by `CombatPreflightService`.

**`pvc_damage_reduction`**: pass down into the tick resolver. Non-zero only for PvC fights.

**Wire-compat kwargs — removed (locked):** both `variance_percent` and the old positional `player_armour_buff` are deleted from `fight_ships` and any internal caller. The "accept-but-ignore" wire-compat period existed only during T3–T9; T10 retires the kwargs alongside `SimpleTTKResolver`, `DUEL_VARIANCE_PERCENT`, and `BOUNTY_PVC_ARMOUR_BUFF_FACTOR`. Grep confirms no internal callers pass these.

### (4) Player stat promotion (§13)

For each HUMAN combatant (i.e. `combatant{1,2}_user_id IS NOT NULL`), inside `fight_ships` when `log_result=True`:

- `total_fights` += 1 (always)
- `total_nukes_fired` += count of `weapon_fire` events emitted by this combatant with subtype `"nuke"` (read from `fight_results.combat_log`)
- `total_module_activations` += count of `module_activation` events emitted by this combatant (Phase-1: cloak + booster + EmergencySystem; passives excluded per §13 — already enforced upstream by T8/T9 not emitting events for passives)

Use `PlayerRepository` (existing — at `services/bot-core/src/persist/repositories/player_repository.py`) to look up the `Player` row by `(guild_id, user_id)` and increment the columns. NPC side: skip cleanly, no DB call, no log noise.

- `BOUNTY_PVC_ARMOUR_BUFF_FACTOR` from `GameConstants` (and any per-guild override plumbing in `guild_config.py` / `config_repository.py` / `config_schema.py` if present — grep before deleting).
- `DUEL_VARIANCE_PERCENT` from `GameConstants`.
- `duel_variance_percent` per-guild override column on `GuildConfig` (currently at `services/bot-core/src/persist/models/guild_config.py:98`) and its echoes in `config_schema.py:21`, `config_repository.py:465`, and the migration row at `revisions/versions/0005_b49_per_guild_game_constants.py:31`.

- `player_armour_buff` parameter from all touched signatures (`fight_ships` itself + any pass-through helpers).
- `variance_percent` parameter from all touched signatures.
- The stale `services/AGENTS.md` line describing `SimpleTTKResolver`-based combat (`services/bot-core/src/services/AGENTS.md:290`) — replace with a one-line pointer to the tick resolver landed in T3–T9.

**Keep populated for wire-compat** (§12 "Legacy `FightStats` wire-compat") — derive from `FightResults.metadata` after the resolver runs; these never participate in the tick resolver:
- `FightStats.raw_hp` = sum of effective start HP across layers
- `FightStats.varied_hp` = `raw_hp` (variance not applied; field kept distinct for legacy reader compat)
- `FightStats.raw_dps` = `damage_dealt / duration_s`
- `FightStats.varied_dps` = `raw_dps`
- `FightStats.ttk` = `duration_s` for the loser, `None` for the winner

**Audit `FightStats.variance_percent`** (`combat_models.py:208,220` and `bounty_service.py:84` consumes it): §12 lists the wire-compat field set explicitly and `variance_percent` is NOT in it. Recommend removing the field from `FightStats` and the caller's payload in this PR; flag for spec confirmation if any external consumer (e.g. an embed) actually surfaces it.

1. Land `CombatLogService.persist` (small, testable in isolation).
2. Extend `db_retention_default` executor (small, mirrors existing pattern).
3. Modify `fight_ships` signature; route through tick resolver (T9 shape) + persist + stat increments.
4. Update each of the 5 callsites one at a time, smoke-testing each.
5. Delete `SimpleTTKResolver` and the four legacy constants/params **LAST** — only after all callers no longer reference them.
6. Land the `duel_variance_percent` column-drop migration last (after no app code references it).

**`variance_percent` kwarg fate (locked):** remove entirely from `fight_ships` and any callsite. Spec §12 retires it alongside `SimpleTTKResolver`; grep confirms no internal callers currently pass it. Same removal applies to the `DUEL_VARIANCE_PERCENT` constant.

**Preflight `pvc_damage_reduction` (locked):** preflight Monte-Carlo passes `pvc_damage_reduction=0.33` for PvC scenarios — matching the actual Silver+ fight the player will run, so `/promote` predictions stay true to the target-tier experience. (If preflight is ever extended to simulate PvP duels, that branch would pass `0.0`; the current `/promote` flow is PvC-only.)

**`FightResults.variance_percent` (locked: remove):** delete the field from the dataclass (`combat_models.py:220`) and the consumer line in `bounty_service.py:84`. Grep `services/discord-gateway/src/` for any embed reader that surfaces `variance_percent` — retire in the same PR. The §12 `FightStats` wire-compat list intentionally excludes this field.

**Stay inside these files** (TODO.md line 128 guardrail): T10 must NOT refactor `duel_service.accept_duel` or `bounty_service.check_system` reward logic beyond the `fight_ships(...)` call replacement. Touching anything else in those methods is scope creep.

**PvC determination at the callsite**: the resolver itself stays `loadouts in → FightResults out` (§12). `pvc_damage_reduction` is set by the caller — 0.33 for PvC contexts, 0.0 for PvP. The resolver does not infer PvC from the loadouts.

**Stat updates inside `fight_ships`** (§13): do NOT push them up to callers. §13 explicitly places this inside the combat-service post-fight handler, gated by `log_result=True`. Wrong-layer suggestions from reviewers should cite §13.

**NPC-side skip**: identify by `combatant{1,2}_user_id IS NULL`. PvC has exactly one NPC side; PvP has zero. Iterate over both slots and skip the NULL one.

**`combat_log.data` is generic `JSON`** (§12): never queryable, no indexes on data fields. Combatant identity is already projected to columns precisely for the §12 future-battle-log query.

**Retention key is `created_at`** (§12), not any internal fight timestamp.

**Existing `db_retention_default` pattern** (`utils/executors/db_retention_executor.py:71-111`): three try/except blocks, one DB session per pass, same INFO log shape (`DBRetention[{job_id}] {pass} pass: deleted={N} cutoff={iso} (retention={H}h)`). Mirror exactly for the new combat-log pass; do NOT consolidate the existing passes.

**`FightStats` wire-compat fields are derived, not stored**: compute from `FightResults.metadata` (T9 output) after the resolver runs. They never enter the tick loop. If T9's metadata schema doesn't carry sufficient HP/duration data, that's a T9 bug — file separately, do not patch into the resolver here.

**`combat_log_id` plumbing**: persist returns the row id; assign to `FightResults.combat_log_id` before returning. Callers put `{summary..., combat_log_id}` into their own `combat_result` payload — already supported by §12 "In-memory production & FightResults mapping".

**`CombatMeta` shape**: §12 references `combat_meta` in `CombatLogService.persist(...)`. If T9 introduced this dataclass, reuse. If not, the implementer should land a minimal `CombatMeta(guild_id: int)` dataclass in `combat_models.py` — anything beyond `guild_id` is already on `FightResults.metadata`. Confirm via grep before inventing.

**Re-verify ALL file:line references before editing.** The line numbers throughout this task (the 5 callsites, the legacy symbols, `guild_config.py:98`, `config_schema.py:21`, `config_repository.py:465`, `0005_*:31`) were captured at decomposition and the code has moved since. Re-grep each anchor by its surrounding text; do not edit blind on a captured line number.

**Timeline serialization (shared with T9).** `FightResults.combat_log` holds `CombatEvent` **dataclass objects**, not dicts (`combat_service.py:711`, stored with a `# type: ignore` against the `list[dict]` annotation). `CombatLogService.persist` must serialize each `CombatEvent` in `data.timeline` (e.g. `dataclasses.asdict(...)`) before writing the `data` JSON — a raw `json.dumps` over the object list will fail. Verify the line ref before relying on it.

**`created_at` has no `server_default` (migration 0011).** The `combat_log.created_at` column is `nullable=False` with **no** `server_default` (`services/bot-core/src/persist/database/revisions/versions/0011_combat_log_and_phase1_stats.py:81`) — unlike the sibling columns in that migration. Every insert therefore MUST go through the ORM so the application-side default supplies the value; a raw-SQL insert would violate the NOT NULL constraint. T10's persist path uses the ORM, so this is fine — noted so no one adds a raw-SQL insert.
