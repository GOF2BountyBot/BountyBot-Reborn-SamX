### D1. All 25 Appendix A constants in `GameConstants`

**File:** `services/bot-core/src/services/game_constants.py`

For each row in Appendix A:
- Add a class attribute on `GameConstants` named exactly as in the table (e.g. `CLOAK_SET_VALUE: float = 0.25`), with the locked default.
- Wire an env-override line inside `GameConstants.load()` using the existing `_track_int` / `_track_float` pattern.
- For the two list-valued constants (`CLOAK_HP_THRESHOLDS_PCT = [66, 33]`, `BOOSTER_HP_THRESHOLDS_PCT = [80, 60, 40, 20]`): the existing helpers only handle scalars. Add a `_track_int_list` helper (or equivalent) that parses a comma-separated env value (`BOUNTYBOT_CLOAK_HP_THRESHOLDS_PCT=66,33`) into a `list[int]`, and uses the default list when unset. Keep the pattern consistent with `_track_int` / `_track_float`.

**Per-guild override:** the existing `resolve_constant(guild_config, field, fallback)` helper at the bottom of `game_constants.py` is the canonical read-site mechanism — it returns `getattr(guild_config, field, None) or fallback`. T1 lands the constants + the env-override path; **no per-tunable column is added to `GuildConfig` in T1**. Per-guild persistence for any specific knob is deferred to whichever later task first needs it (resolver tasks will read via `resolve_constant`; the helper handles the missing-column case natively).

Done when: `python -c "from services.game_constants import GameConstants; print(GameConstants.CLOAK_SET_VALUE)"` returns `0.25`, and every Appendix A name resolves the same way; `BOUNTYBOT_CLOAK_SET_VALUE=0.30 python -c "from services.game_constants import GameConstants; GameConstants.load(); print(GameConstants.CLOAK_SET_VALUE)"` returns `0.30`.

## Risk / notes

- **Per-guild override columns land in T2.** §0.1 mandates a per-guild override path for every Appendix A constant, matching the existing `GuildConfig`-column pattern (set via the existing `admin_config` commands). T1 adds the 25 `GameConstants` entries + the env-override path; **T2 adds the 25 matching `GuildConfig` SQLAlchemy model fields and migration** as part of its bundled schema work. The existing `resolve_constant(guild_config, field, fallback)` helper handles the gap cleanly — it returns `getattr(guild_config, field, None) or fallback`, so the constants resolve to their defaults until T2 lands.
- **`accuracy_modifier` removal — confirm no dangling refs.** The field is documented "unused in SimpleTTKResolver" but a paranoid `rg "accuracy_modifier" services/` (case-sensitive) before deletion is cheap insurance. `ModuleStats.accuracy_modifier` will appear in those results and must NOT be touched.
- **`manual_turret_mode` persistence gap.** D3 reads from `PlayerShip` via `getattr(..., "manual_turret_mode", False)` because T2 has not yet added the column. Once T2 lands, the `getattr` defaults harmlessly. Do not add the column in T1 — that's T2's migration.
- **List-valued env vars.** The existing `_env_int` / `_env_float` helpers don't cover the two HP-threshold lists. A `_track_int_list` helper parsing `"66,33"` → `[66, 33]` is the minimal addition; mirror the `_overrides.append(...)` logging line so the env-override visibility stays consistent.
- **Appendix A naming nit.** The footnote under Appendix A: "Names with `BOUNTYBOT_` prefix are listed verbatim where the existing convention uses the prefix in the env name; others use the unprefixed `GameConstants` name (the runtime env override is `BOUNTYBOT_<NAME>` in all cases)." Use the unprefixed name as the class attribute in every case (`CLOAK_SET_VALUE`, not `BOUNTYBOT_CLOAK_SET_VALUE`); the env-var path is always `BOUNTYBOT_<NAME>`.
- **`CombatEvent.type` typing.** The spec calls the vocabulary "extensible" (§12). Type the field as `str` (not a closed `Literal`). The `CombatEventType` literal/Final names are documentation + reusable identifiers for emit-site code in T3+, not a closed enum.
- **`COMBAT_LOG_RETENTION_HOURS` naming.** Land as `GameConstants.COMBAT_LOG_RETENTION_HOURS` (unprefixed); env override is `BOUNTYBOT_COMBAT_LOG_RETENTION_HOURS` per the Appendix A footnote convention. Consistent with the existing `BOUNTY_RETENTION_HOURS` / `DUEL_RETENTION_HOURS` / `AUDIT_RETENTION_DAYS` family. T10 wires it into `db_retention_default`.
