**File:** `services/bot-core/src/services/combat_service.py` (alongside `SimpleTTKResolver`).

### D3. Tick loop — Appendix B phase ordering

The resolver runs a `for tick in range(MAX_FIGHT_TICKS):` loop. Each tick body executes the Appendix B phases in canonical order, C1 before C2 within each phase. T3 implements:

| Phase | T3 behaviour |
|---|---|
| **1. Decrement cooldowns** | `-= TICK_MS` on every entry in `weapon_cooldowns` and `module_cooldowns`. Floor at 0 (or leave negative — see Risks). C1 first, then C2. |
| **2. Apply regen pulses** | Shield regen + repair-bot regen per §3 dormancy + integer-flush rules. C1 pulses logged before C2's. Emit `regen` events with `{layer, amount, hp_after}`. |
| **3. Evaluate weapon firings** | **STUB — clearly named no-op placeholder.** Wire a `# T5: weapon firing evaluation` marker, possibly a `_evaluate_weapon_firings(state)` method that returns an empty list. Do NOT call `weapon_accuracy()`. |
| **4. Apply damage** | T3 has no fire phase, so no damage events arrive. The damage-application helper exists (D4) and is unit-tested directly. The phase scaffolding lives in the loop but processes an empty per-tick damage queue. |
| **4a. EmergencySystem** | **STUB — `# T9: EmergencySystem evaluation`.** No-op. |
| **4b. HP clamp** | Implemented (defensive — no damage in T3 means no negative HP, but the clamp is part of the canonical phase order). C1 then C2. |
| **5. HP-threshold checks** | **STUB — `# T8: HP-threshold module activations (cloak / booster)`.** No-op. |
| **6. Update distance** | Passive closure: `current_distance = max(MIN_DISTANCE_M, current_distance - (BASE_SHIP_SPEED_MPS * 2) * (TICK_MS / 1000))`. Booster push is T8. Shock-blast reset is T6. Emit `distance` event when distance actually changes (i.e. while above floor — once it pins to floor, stop emitting). |
| **7. Emit timeline events** | Already incremental — each phase appends events to `FightResults.combat_log` in processing order. This step is *the contract that the events are flushed for the tick*, not a separate emission step. |
| **8. Check termination** | Both sides hull ≤ 0 → `outcome=stalemate, reason=mutual`. Exactly one → `outcome=win, reason=hp_depleted`. Tick == `MAX_FIGHT_TICKS - 1` with both alive → `outcome=stalemate, reason=time_cap`. Emit `fight_end` and exit. |

The loop is bounded by `MAX_FIGHT_TICKS`; if it falls out of the `for` with no termination, treat it as `time_cap`.

### D4. Damage-application helper

A function (`_apply_damage(state, raw_damage, *, source, pvc_damage_reduction, attacker_is_npc)` or similar) that:

1. **Scales by PvC DR** if `pvc_damage_reduction > 0.0` AND `state.is_player` is True. Applied **first**, before stacking. Per §3: "DR is the *first* modifier applied to a damage event before it walks the layers." Per §3 also: covers ALL incoming damage including the firer's own nuke self-damage (relevant for T6, harmless guidance here).
2. **Walks shield → armour → hull**, decrementing in order. Overkill within a single damage event carries to the next layer (so an 800-damage hit on a 50-shield/200-armour/100-hull combatant lands as 50/200/100 = 350 absorbed + 450 overkill on hull → `current_hull = -450`). HP is allowed to go transiently negative per §3 / Appendix B step 4. Step 4b clamps to 0 at end of phase.
3. **Emits a `damage` event** with `{amount: raw_damage, breakdown: {shield, armour, hull}, hp_after: {shield, armour, hull}, source}`.
4. **Emits a `layer_depleted` event** for each layer that transitioned from `> 0` to `≤ 0` in this damage application. Order: shield first, then armour. (Hull depletion is the terminal condition — step 8 handles it via `fight_end`, not `layer_depleted`.)

Helper is pure-on-state — takes the receiving combatant, mutates it, returns nothing. No knowledge of attacker except via `source` (which is a dict carried into the event data; T3 passes `{"placeholder": True}` since nothing fires).

### D5. PvC determination — the explicit decision point

§3 says DR applies to "the player-side combatant in a PvC fight"; §12 says "for PvC, player = C1, NPC = C2"; the future `fight_ships(...)` signature (§12 Public API) carries `pvc_damage_reduction: float = 0.0`.

**Recommended path for T3:** `TickResolver.resolve` accepts `pvc_damage_reduction: float = 0.0` as a kwarg. The resolver itself does NOT introspect loadouts to figure out who's the player — it relies on the **caller's convention** that C1 is the player in PvC. Specifically:

- `pvc_damage_reduction > 0.0` → set `combatant1.is_player = True`, `combatant2.is_player = False`.
- `pvc_damage_reduction == 0.0` → both `is_player = False` (PvP or preflight; no DR applied to either side).

This mirrors the §12 `fight_ships(..., pvc_damage_reduction=...)` cutover signature T10 will land. The resolver does not need an explicit `is_pvc: bool` or per-loadout player flag.

Read `LoadoutBuilder.from_player` vs `from_criminal_ship` (`services/bot-core/src/services/loadout_builder.py`) once to confirm there's no existing `is_player` attribute being set on `ShipLoadout` — there isn't; that's why the caller-side convention is the cleanest landing for T3.

This convention is now canonical via the §12 callsite table (per Q7 lock): `pvc_damage_reduction` is set explicitly per caller (0.33 for PvC, 0.0 for PvP).

### D6. Regen mechanics — integer-flush schedules

**Shield regen** (one independent track per shield module — sums conceptually, but the schedule per spec is per-module):

- Period for module M: `N_M = ceil(M.shield_recharge_ms / M.shield_capacity / TICK_MS)` ticks per +1 HP.
- Implementation tip: precompute `(N_M)` for each shield module at combatant init. Each tick (when shield is non-full), increment a per-module accumulator; when it crosses its period, emit +1 HP and reset.
- Dormancy: while `current_shield == max_shield`, accumulators are dormant. When shield drops below max (first damage), accumulators start at 0. When shield returns to max, partial accumulation is **discarded**.

**Repair Bot regen** (hull-first, then armour):

- Per-tick delta = `(max_hull + max_armour) × rate × (TICK_MS / 1000)`. Default Ketar I = 0.025 (2.5 %/s); Ketar II = 0.050 (5.0 %/s).
- Accumulate the float delta into a `repair_bot_regen_accumulator: float` per tick; when the accumulator ≥ 1.0, flush `int(accumulator)` to HP and subtract that integer from the accumulator. HP storage stays integer.
- Fill order: while `current_hull < max_hull`, all flushed HP goes to hull. Once hull is at max, switch to armour. If both are at max, the accumulator is dormant (no ticking). When either layer drops back below max, accumulator starts at 0.
- Per §3: this is "the same `+1 HP every N ticks` integer-flush discretization as shield regen (pattern shared; layers disjoint)" — but the rate is percent-of-max, not capacity / recharge_ms. Implementer's call whether to express it as an N-tick period (derivable) or as an accumulator (more natural for a percent-of-max rate). The accumulator form is closer to the spec wording.

**Dormancy assertion** (instrumented): when a layer is at max, the resolver MUST NOT call `_tick_shield_regen` / `_tick_repair_bot_regen` on the relevant accumulator. Make this observable — either an `assert` (cheap; T3 tests can rely on it) or a counter exposed for tests.

### D7. Distance closure

- Per-tick decrement: `BASE_SHIP_SPEED_MPS × 2 × (TICK_MS / 1000)` = 300 × 0.01 = 3 m/tick. Use the formula form (not the literal 3), reading constants from `GameConstants`.
- Floor: `MIN_DISTANCE_M` (300 m).
- No upper bound (per §2). Booster push and shock-blast reset both deferred (T8 / T6).
- Emit `distance` event with `{from, to, cause: "closure"}` only on ticks where `current_distance` actually changes. Once pinned at floor, no further `distance` events.

### D8. Termination matrix (§9)

Map outcomes to `summary.outcome` and `summary.reason` per the §9 table:

| Condition | `outcome` | `reason` |
|---|---|---|
| Exactly one side hull ≤ 0 at end of tick | `win` | `hp_depleted` |
| Both sides hull ≤ 0 on the same tick | `stalemate` | `mutual` |
| Tick counter reaches `MAX_FIGHT_TICKS` with both alive | `stalemate` | `time_cap` |

`fight_end` event payload: `{winner, reason, duration_ticks, final_hp: {c1: {shield, armour, hull}, c2: {…}}}`. On `stalemate`, `winner = null`.

Populate `FightResults.winner_name` / `loser_name` / `is_stalemate` from the matrix. `FightResults.metadata` carries the resolver metadata (`{tick_ms, total_ticks, resolver: "tick_v1", pvc_damage_reduction}` per §12 — T3 lands the metadata block fully; T9 will extend with the summary builder).

## Risk / notes

- **Appendix B step order is canonical (TODO.md line 125).** The implementer MUST NOT reorder regen / damage / threshold phases, even if a reordering "looks cleaner" or "saves a branch." The mutual-kill, finishing-blow, and ES-on-cumulative-hull behaviours all fall out of this exact order. Reordering breaks future tasks silently.
- **"Stay inside these files" (TODO.md line 128).** T3 is a cross-cutting risk area. The implementer should resist temptation to refactor `combat_models.py` (the `WeaponStats` / `ModuleStats` shape stays as T1 left it — module/weapon plumbing is for T4–T9) and should not touch `combat_service.fight_ships` beyond adding the `TickResolver` class definition next to `SimpleTTKResolver`.
- **PvC determination — explicit decision point.** Recommendation (above, D5): `pvc_damage_reduction: float = 0.0` kwarg on `TickResolver.resolve`; non-zero means C1 is the player-side; resolver does NOT introspect loadouts for an `is_player` field. This aligns with the §12 / T10 cutover signature. The implementer should flag this prominently in the PR description so reviewers can sign off explicitly — it's the one decision T3 makes that downstream tasks will inherit.
- **Repair Bot `HPps` seed values are stale (§3).** Do NOT consume `extra_atts.HPps` (7 / 15 — wrong). Use the locked rates: Ketar I = 0.025, Ketar II = 0.050. Read from `GameConstants.KETAR_I_REPAIR_PCT_PER_SEC` / `KETAR_II_REPAIR_PCT_PER_SEC` (Appendix A). The matching mechanism (which module is Ketar I vs II) comes from the module name; for T3 the implementer can hard-code the two known names — T8/T9 may refactor this if a module-tier discriminator lands.
- **Integer HP only at the layer boundary.** All HP storage is `int`. Intermediate calculations (PvC DR scaling, regen accumulators, future nuke falloff in T6) may carry `float` — the integer boundary is enforced when an HP delta is committed to a layer. Use Python `round()` at that boundary (§3 + §7.8). Per-tick *per-layer* HP delta is integer; per-tick per-event intermediate may not be.
- **Cooldown decrement on zero.** §1: cooldowns decrement by 10 ms per tick. Once at 0, further decrements would go negative. Floor to 0 (recommended) OR leave negative-but-treat-as-ready (works too). Floor is simpler and matches the §1 "≤ 0" gate semantics. Be consistent across weapon and module cooldown maps.
- **Distance closure literal.** Per §2: `BASE_SHIP_SPEED_MPS × 2` = 300 m/s relative, so per tick = 3 m. Read the constants — do not hard-code `3`. The closure rate is the only place "× 2" enters; passive closure is symmetric (both sides approach at `BASE_SHIP_SPEED_MPS`).
- **Legacy `SimpleTTKResolver` stays.** The two resolvers coexist until T10. `fight_ships(...)` continues to route to `SimpleTTKResolver`; new resolver is reachable only by direct instantiation (e.g. in tests). Do NOT add a feature flag, env switch, or callsite branch — T10 owns the cutover.
- **`CombatResolver` Protocol shape.** The existing protocol takes `CombatStats × 2 + variance_percent`. `TickResolver.resolve` takes `ShipLoadout × 2 + pvc_damage_reduction`. They are not interchangeable. T3 does NOT widen the Protocol — T10 reconciles it when `SimpleTTKResolver` retires. If a duck-typed shared protocol is tempting, resist; the two signatures diverge by design and the Protocol will retire with the legacy resolver.
- **Time-cap edge case.** `range(MAX_FIGHT_TICKS)` runs ticks 0…17999 — 18,000 ticks total. `time_cap` fires when the loop falls through with both alive. Phase 8 on the final iteration (tick 17999) can also detect `time_cap` and emit `fight_end` from inside the loop — both shapes work; pick one and be consistent.
- **No `weapon_fire` / `cooldown_end` events.** T3 decrements cooldowns at step 1 but does NOT emit `cooldown_end` (T5's job once weapons actually fire). The `weapon_cooldowns` map exists and ticks; it just doesn't gate anything yet.
- **Damage rounding policy (locked).** Per §3: `round()` at the integer boundary; intermediate damage values may carry float through PvC DR scaling, falloff (T6 nuke), and any composition step. The final per-layer HP delta committed to shield/armour/hull is integer.
