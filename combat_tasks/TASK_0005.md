# TASK_0005 — T5: Primary weapons + PrimaryWeaponMod

> **Scope:** make primary weapons functional end-to-end inside the T3 tick loop —
> per-weapon cooldown decrement, binary range gate, accuracy roll, damage
> emission via T3's stacking helper, plus the §7.8 PrimaryWeaponMod pre-pass.
> First "things actually fire" milestone. Secondaries (T6), turrets (T7), and
> all module activations (T8 / T9) remain stubbed.

## Spec references

The implementer has the full `/proj/COMBAT_SPEC_LOCKED.md` in context. T5 is governed by:

- **§1** — tick + cooldown decrement semantics. T3 stubbed the decrement; T5 makes it functional and adds `cooldown_end` emission.
- **§2** — range gating: `current_distance ≤ weapon.range_m` (binary). No in-range degradation for primaries.
- **§4** — damage type model. Phase-1 is **physical only**. `emp_damage` is IGNORED regardless of value. Pure-EMP primaries fire normally and apply 0 HP delta. Hybrid (physical > 0 AND emp > 0) applies only the physical component.
- **§5 / §6.1** — primaries have NO in-range distance penalty. Range is a pure binary gate. Accuracy = §5 `pilot_primary_acc` (already on `CombatantState` from T4) passed through `weapon_accuracy(pilot_acc, weapon)`.
- **§6.1** — primary weapon mechanics: hit damage = `damage_per_shot`; cooldown = `loading_speed_ms`.
- **§7.8** — PrimaryWeaponMod: per-shot `damage_pct` + `fire_rate_pct`, applied at combatant init. Effective stats:
  - `effective_damage_per_shot = round(damage_per_shot × (1 + damage_pct / 100))`
  - `effective_loading_speed_ms = round((loading_speed_ms / (1 + fire_rate_pct / 100)) / TICK_MS) × TICK_MS`
  - No floor on `effective_damage_per_shot`. `dpsMultiplier` is IGNORED by the tick resolver.
- **§10** — PrimaryWeaponMod is unique-equip (loadout-builder concern). T5 is defensive: if more than one is somehow present, the first wins and the rest are ignored. T5 does NOT validate the loadout contract.
- **§12** — `weapon_fire`, `damage`, `cooldown_end` event payload shapes.
- **Appendix B** — tick step order. T5 implements phase 3 (fire eval) and contributes to phase 4 (damage application), respecting fire-vs-apply separation.

## Deliverables

T5 delivers a fully functional primaries-fire path. No secondaries, no turrets, no module mechanics.

### D1. PrimaryWeaponMod pre-pass at combatant init

**File:** combatant init in `services/bot-core/src/services/combat_service.py` (T3's `_init_combatant`-equivalent).

At combatant construction, before the tick loop begins:

1. Scan `loadout.modules` for an equipped `PrimaryWeaponModModule` (§10 STI discriminator). Identify by `ModuleStats.name` (or whichever field carries the seed type discriminator — verify against existing module-typing pattern at impl time; the two Phase-1 seed entries are `"Nirai Overdrive"` and `"Nirai Overcharge"` per §7.8).
2. **Unique-equip defensive guard:** if multiple PrimaryWeaponMods are present (should never happen post-loadout-builder per §10), **first wins**; log a WARN once with both names and the player/criminal identifier so the upstream invariant violation is observable.
3. Read `damage_pct` and `fire_rate_pct` from the mod's `extra_atts` (integer percentages, can be negative).
4. For each primary weapon in `loadout.weapons`, compute:
   - `effective_damage_per_shot = round(damage_per_shot × (1 + damage_pct / 100))` — integer. **No floor guard.** Base-0 EMP primaries stay 0.
   - `effective_loading_speed_ms = round((loading_speed_ms / (1 + fire_rate_pct / 100)) / TICK_MS) × TICK_MS` — snapped to `TICK_MS` boundary.
5. If no PrimaryWeaponMod is equipped, `effective_damage_per_shot = damage_per_shot` and `effective_loading_speed_ms = loading_speed_ms` (already a clean `TICK_MS` multiple per §1 — no snap needed but the formula is identity-safe).
6. Store the per-weapon resolved stats on `CombatantState` in a structure the tick loop can index (e.g. `effective_primaries: list[PrimaryWeaponRuntime]` where each carries `{name, effective_damage_per_shot, effective_loading_speed_ms, range_m, is_pure_emp, weapon_stats_ref}` or equivalent shape — implementer's choice as long as it's introspectable for tests per acceptance criterion).

**Note:** The seed `dpsMultiplier` is read **only** for the SimpleTTKResolver and the item-detail embed (§7.8 legacy retention). T5's pre-pass MUST NOT consume it.

### D2. Range gate

**File:** phase 3 inside the tick loop in `combat_service.py`.

For each primary weapon on a combatant, gate firing on:

```
current_distance ≤ weapon.range_m   # binary, no degradation
```

`range_m` is the seed value (PrimaryWeaponMod does NOT modify range — §7.8 covers `damage_pct` + `fire_rate_pct` only). A weapon outside its range does not fire, does not roll accuracy, does not emit `weapon_fire`. Its cooldown still ticks down at phase 1.

Boundary semantics: `≤` (closed interval). At `current_distance == range_m` the weapon fires. At `range_m + 1` it does not.

### D3. Cooldown decrement → functional

**File:** phase 1 inside the tick loop in `combat_service.py` (T3 stub).

For each primary weapon on each combatant:

- `cooldown_remaining_ms -= TICK_MS`
- If the value transitioned from `> 0` to `≤ 0` this tick, emit a `cooldown_end` event with `data: {system: weapon.name}` (the §12 `cooldown_end` payload shape: `{system}`).
- Floor at 0 (don't accumulate negative values — keeps the gate semantics clean and matches T3's existing cooldown-floor convention).

Initial state at tick 0: all primaries enter combat with `cooldown_remaining_ms = 0` (per §1 / T3 D2). On tick 0 they evaluate immediately at phase 3 — no warmup tick.

### D4. Fire evaluation — phase 3

**File:** phase 3 (`# T5: weapon firing evaluation` marker T3 left in place) in `combat_service.py`.

For each combatant, for each primary weapon:

1. **Gate checks** (in this order — short-circuit at the first failure):
   - `cooldown_remaining_ms ≤ 0` (weapon ready)
   - `current_distance ≤ range_m` (in-range per D2)
2. **Compute accuracy** — call `weapon_accuracy(combatant.pilot_primary_acc, weapon_stats)` (T1 passthrough; T4 supplies `pilot_primary_acc` on `CombatantState`). The §5 layered clamp to `[ACCURACY_CLAMP_MIN, ACCURACY_CLAMP_MAX]` has already been applied by T4 — do NOT re-clamp here.
3. **Roll RNG** — `roll = rng.random()`. `hit = roll < accuracy`.
4. **Record the hit** in a per-tick "pending damage" queue keyed by the receiving combatant. The queue carries `{attacker_state, target_state, weapon_runtime, hit, accuracy, applied_damage: effective_damage_per_shot, source_subtype: "primary"}`. Phase 4 drains it. **DO NOT apply damage inline in phase 3** — Appendix B fire-vs-apply separation is what makes mutual-fire-on-lethal-tick correct.
5. **Emit `weapon_fire` event** with §12-conformant payload:
   ```
   {slot: "primary", subtype: "primary", weapon: weapon.name, hit: bool, accuracy: float}
   ```
   Emit regardless of hit/miss. `accuracy` is the resolved value at fire time (D5 / §12 — don't recompute later for the log).
6. **Reset cooldown** — `cooldown_remaining_ms = effective_loading_speed_ms`. Reset happens on both hit AND miss (the weapon fired either way; the cooldown is wall-clock, not outcome-dependent).

Iteration order across primaries on a single combatant: insertion order from `loadout.weapons` is fine — consistent ordering matters for test determinism but the spec doesn't constrain it further.

### D5. Damage application — phase 4

**File:** phase 4 in `combat_service.py` (T3 placeholder).

Drain the per-tick pending-damage queue, in canonical order (C1 attacker hits first, then C2 attacker hits — Appendix B C1-before-C2 within phase 4):

For each `hit=True` entry:

- Call T3's `_apply_damage(target_state, raw_damage=effective_damage_per_shot, source={"subtype": "primary", "weapon": weapon.name, "attacker": attacker_state.name}, pvc_damage_reduction=..., ...)` — the helper handles PvC DR scaling, shield → armour → hull walking, overkill carryover, integer-flush, `damage` event emission (with `{amount, breakdown, hp_after, source}` per T3 D4), and `layer_depleted` emission.
- For `hit=False` entries, **NO `damage` event is emitted** — the miss is fully captured by the phase 3 `weapon_fire` event with `hit=false`. Don't synthesize a zero-amount damage event.

**Pure-EMP primary** (e.g. `luna_emp_mk_i`, `sol_emp_mk_ii`, `dia_emp_mk_iii` per §4 inventory): on hit, `effective_damage_per_shot` is 0 — call the damage helper with `raw_damage=0`. The helper emits `damage` with breakdown `{shield: 0, armour: 0, hull: 0}`, `amount: 0`, `hp_after` unchanged. No `layer_depleted` fires. This is the canonical 0-HP-delta path. Do NOT special-case-skip the damage helper call; let it record a zero-amount event so the combat log shows the EMP-blaster landed.

**Hybrid primary** (any seed entry with both `damage_per_shot > 0` AND `emp_damage > 0`): apply ONLY the physical `damage_per_shot` track. `emp_damage` is ignored regardless of value (§4). The mod-baked `effective_damage_per_shot` already carries the physical-only resolved value; the resolver never reads `emp_damage` from the weapon.

### D6. Confirm initial cooldown state holds post-T5 init

Per §1 / T3: all weapons start at `cooldown_remaining_ms = 0`. T5's D1 pre-pass adds `effective_*` fields but MUST NOT alter the initial cooldown. Confirm in tests (tick-0 firing is a category in D7).

## Out of scope

- **No secondaries (T6).** Rocket / missile / cluster-missile / nuke / shock-blast all remain stubbed at phase 3.
- **No turrets (T7).** Auto-turret accuracy multiplier, manual-turret-mode flag branching, plasma-collector handling — all T7. T5 assumes `manual_turret_mode=false` is in effect and primaries fire normally; the flag exists on `ShipLoadout` (T1) and on `CombatantState` (T3) but T5 does NOT consult it. - **No `module_activation` event emission from T5.** Only `weapon_fire`, `damage` (via T3 helper), `cooldown_end` — and the T3-era events (`fight_start`, `fight_end`, `regen`, `layer_depleted`, `distance`) which T5 doesn't touch.

T5 maintains its own internal `effective_primaries`-style runtime list on `CombatantState` regardless.

## Risk / notes

- **`fire_rate_pct` sign convention — positive = faster (lower cooldown).** The formula is `effective_loading_speed_ms = round((loading_speed_ms / (1 + fire_rate_pct / 100)) / TICK_MS) × TICK_MS`. A naive read of "fire_rate_pct +20 means 20% slower" inverts the mechanic. Nirai Overdrive: `+20` → `1000 / 1.2 = 833.33` → snap to `830 ms`. A directional unit test (D7 categories 5 + 6) guards this.
- **`TICK_MS` snap is on the cooldown, not on damage.** Two different rounding paths in §7.8:
  - Damage: `round()` to nearest integer.
  - Cooldown: `round(... / TICK_MS) × TICK_MS` to nearest 10 ms multiple.
  Don't accidentally apply `TICK_MS` snap to damage or `round()` to cooldown.
- **No floor on `effective_damage_per_shot` (§7.8).** Base-0 EMP-blaster primaries (Luna / Sol / Dia per §4 inventory) stay 0 after any mod. Standard primaries (`damage_per_shot ≥ 2`) won't collapse to 0 under −10% (`2 × 0.9 = 1.8 → round → 2`). A floor guard would actively contradict the spec — do NOT add one.
- **PrimaryWeaponMod scope is primaries ONLY (§7.8).** When T6 / T7 implementers come through:
  - T6 (secondaries) MUST NOT apply `damage_pct` / `fire_rate_pct` to rockets / missiles / cluster-missiles / nukes / shock-blast.
  - T7 (turrets — auto AND manual) MUST NOT apply the mod stats.
  T5 already enforces this by computing the `effective_*` stats only for primaries during init; the per-weapon runtime list is keyed to primary weapons. Document inline so T6 / T7 implementers see the boundary.
- **Hybrid / pure-EMP — §4 is unambiguous.** `emp_damage` is IGNORED regardless of value. The resolver MUST NOT conditionally check guild settings, scanner tier, or anything else. The only physical track applies. Phase-2 EMP support will redesign this entirely; Phase-1 primaries are physical-only.
- **Fire/apply separation (Appendix B).** Phase 3 RECORDS hits; phase 4 APPLIES damage. The mutual-fire-on-the-lethal-tick case (both sides drop to ≤ 0 hull on the same tick) only works correctly if phase 3 doesn't mutate HP. Don't shortcut by calling the damage helper inline in phase 3, even if it "looks cleaner."
- **`weapon_fire` accuracy is the resolved value at fire time (§12).** The event log records what the weapon rolled against. If the implementer later wants to recompute accuracy from the snapshot for any reason (e.g. UI replay), the stored value is authoritative. Don't re-derive from `pilot_primary_acc` later — it changes per tick.
- **Damage delta is integer (T3 enforced this).** `effective_damage_per_shot` is integer (from `round()`). The damage helper's stack walk subtracts integers. PvC DR scaling produces a float intermediate (`100 × 0.67 = 67.0`) which T3's helper rounds to integer per §3 / per T3's open-question resolution. T5 doesn't need to re-handle this — the helper does.
- **`cooldown_end` tick-0 ambiguity.** Cooldown starts at 0; phase 1 decrement at tick 0 goes 0 → −10 → floor to 0. Did a transition `>0 → ≤0` occur? Strict reading: no, the cooldown was never above 0. Pragmatic reading: the floor itself constitutes a transition. The spec (§12 + Appendix B) is silent on the exact tick-0 semantics. **Recommended:** emit `cooldown_end` only on a real `>0 → ≤0` transition (no tick-0 emission for weapons that start at 0). This keeps the event meaningful (a `cooldown_end` event = "this weapon is now ready for the first time since it fired"). Document in the PR; the test in D7 category 16 should match the chosen semantic.
- **Iteration order of primaries within a combatant.** Insertion order from `loadout.weapons` is the natural choice. The spec doesn't constrain it; tests should not depend on cross-weapon ordering at fine granularity except where Appendix B explicitly says so (C1 before C2 across combatants; phase 3 before phase 4 within a tick). Internal weapon-list iteration is an implementation detail.
- **Primary `weapon_fire` payload (locked in §12's per-subtype table):** `{slot: "primary", subtype: "primary", weapon, hit, accuracy}`. Both `slot` and `subtype` are the literal string `"primary"` — redundant for primaries but consistent with the spec's uniform per-subtype shape across all weapon classes.
- **Miss event shape (locked):** a miss emits `weapon_fire(hit=false, accuracy=...)` alone — NO follow-on `damage` event. §12's `damage` event is defined as "HP applied after a hit"; misses skip the damage phase entirely. (Contrast with ES invuln from Q5, which DOES emit `damage(amount: 0, blocked_by: ...)` because the shot conceptually landed.)
