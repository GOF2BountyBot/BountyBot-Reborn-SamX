### D1. `compute_pilot_accuracy(...)` — the layered formula + cloak override

**File:** `services/bot-core/src/services/combat_balance.py` (extend, alongside the T1 surfaces)

```python
def compute_pilot_accuracy(
    *,
    combatant_base: float,                # 0.60 player / 0.50 NPC
    own_scanner_bonus_pp: float,          # 0 / 5 / 10
    own_thruster_bonus_pp: float,         # already ramped — pre-multiplied by ramp()
    opponent_booster_debuff_pp: float,    # already scaled by k_boost — pre-multiplied
    opponent_cloak_active: bool,
    cloak_set_value: float,               # GameConstants.CLOAK_SET_VALUE (per-guild overridable)
    clamp_min: float,                     # GameConstants.ACCURACY_CLAMP_MIN
    clamp_max: float,                     # GameConstants.ACCURACY_CLAMP_MAX
) -> tuple[float, float]:
    """Return (pilot_primary_acc, pilot_turret_acc) per §5 / §6.3.

    Cloak override REPLACES the layered formula (does NOT stack). It applies
    to BOTH the primary and turret variant. The turret variant differs from
    the primary variant ONLY by excluding the thruster bonus term.
    """
```

Behaviour:

- **Cloak active path** (opponent's cloak is active this tick): return
  `(clamp(cloak_set_value, clamp_min, clamp_max), clamp(cloak_set_value, clamp_min, clamp_max))`.
  The cloak override is a single set-value that supersedes everything; turret variant gets the same value here. T7 layers `AUTO_TURRET_ACCURACY_MULTIPLIER` (0.85) on top of `pilot_turret_acc` later — that multiplier is **not** applied in T4 (see Out of scope).
- **Cloak inactive path**: build the layered formula in **percentage-points** consistently. Recommended:
  - `layered_pp = combatant_base * 100 + own_scanner_bonus_pp + own_thruster_bonus_pp − opponent_booster_debuff_pp`
  - `pilot_primary_acc = clamp(layered_pp / 100, clamp_min, clamp_max)`
  - `pilot_turret_acc = clamp((layered_pp − own_thruster_bonus_pp) / 100, clamp_min, clamp_max)` (re-derive without the thruster term — do **not** subtract `own_thruster_bonus_pp` from `pilot_primary_acc` after clamping; clamp each variant independently to avoid bound-interaction bugs).
- **Pure function.** No I/O, no logging, no GameConstants reads internally — caller passes everything. Easy to unit-test deterministically.

### D2. `thruster_ramp(current_distance, *, thruster_window_m, min_distance_m) -> float`

**File:** `services/bot-core/src/services/combat_balance.py`

Implements §5 thruster ramp:

```
ramp = clamp((thruster_window_m − current_distance) / (thruster_window_m − min_distance_m), 0.0, 1.0)
```

- Returns 0.0 when `current_distance >= thruster_window_m` (default 750 m).
- Returns 1.0 when `current_distance <= min_distance_m` (default 300 m).
- Linear interpolation between — at 525 m (midpoint), ramp = 0.5.
- Pure function. No side effects.

This is the **passive evaluator** for the thruster term. T8 will plug in module-presence (which modules are equipped and what their `effect_pct` is); T4 only delivers the ramp function so T8 can call `effect_pct × THRUSTER_ACCURACY_BONUS_FACTOR × ramp(current_distance, ...)` later.

### D3. `booster_debuff_pp(effect_pct, *, k_boost) -> float`

**File:** `services/bot-core/src/services/combat_balance.py`

Implements §5 booster debuff:

```
debuff_pp = effect_pct × k_boost
```

- Returns a **percentage-points** value (e.g. Polytron with `effect_pct = 300` and `k_boost = 0.10` → `30.0` pp).
- Sign convention: the function returns a **positive** debuff magnitude. The *caller* (D1) subtracts it from the attacker's accuracy. This makes the direction explicit at the call site and reduces sign-confusion bugs.
- Pure function. No clamping internally — the layered formula's `[0.05, 0.99]` clamp is the only bound.

T4 ships the function. T8 will wire it to "is the defender's booster currently active? if yes, supply `effect_pct`" — until then, callers in T4 / T3 pass 0.0 (no debuff).

### D4. Scanner tier resolution helper

**File:** `services/bot-core/src/services/combat_balance.py`

```python
@dataclass(frozen=True, slots=True)
class ScannerTier:
    tier: str               # "A" | "B" | "C"
    accuracy_bonus_pp: float  # 0 / 5 / 10
    missile_tracking_active: bool
```

```python
def resolve_scanner_tier(
    loadout: ShipLoadout,
    *,
    tier_b_bonus_pp: float,   # GameConstants.SCANNER_TIER_B_BONUS_PP
    tier_c_bonus_pp: float,   # GameConstants.SCANNER_TIER_C_BONUS_PP
) -> ScannerTier:
    """Inspect equipped modules; return (tier, bonus_pp, missile_tracking_active).

    Per §7.1: combat scanner is unique-equip on its own subclass. Plasma scanner
    shares the ScannerModule class but is inert in combat — discriminate by
    module name / subtype, not just class membership.
    """
```

Behaviour:

- **No combat scanner equipped** → Tier A: `(tier="A", accuracy_bonus_pp=0.0, missile_tracking_active=False)`.
- **Telta Quickscan OR Telta Ecoscan equipped** → Tier B: bonus = `tier_b_bonus_pp` (default 5), tracking True.
- **Hiroto Proscan OR Hiroto Ultrascan equipped** → Tier C: bonus = `tier_c_bonus_pp` (default 10), tracking True.
- **Plasma scanner equipped, no combat scanner** → Tier A (plasma is inert per §7.1).
- **Both plasma and combat scanner equipped** → use the combat scanner's tier (plasma is inert in combat regardless of presence).
- **Multiple combat scanners equipped** — loadout-builder is supposed to dedupe (unique-equip per §10), but be defensive: pick the highest-tier scanner present. Document the assumption inline.
- Pure function over the loadout snapshot. **Stateless** — same loadout returns the same `ScannerTier` across calls (verified by a test).

**Module identification strategy:** T4 reads from `ShipLoadout.modules: list[ModuleStats]` (T1 / T3 surface). `ModuleStats.name` carries the display name (e.g. `"Telta Quickscan"`). T4 uses the name as the discriminator — hard-code the four combat-scanner names in a module-level frozen mapping inside `combat_balance.py`:

```python
_SCANNER_TIER_BY_NAME: dict[str, str] = {
    "Telta Quickscan": "B",
    "Telta Ecoscan": "B",
    "Hiroto Proscan": "C",
    "Hiroto Ultrascan": "C",
}
```

This is fragile against future scanner additions but matches the §7.1 fixed inventory and is the cleanest landing for T4. A refactor to a `ModuleStats.combat_scanner_tier` field would be appropriate when more scanners land — flag as a future cleanup, not a T4 deliverable.

### D7. Deterministic-RNG seam

**File:** `services/bot-core/src/services/combat_service.py`

T3's `TickResolver.resolve(...)` does not currently take an RNG (no firing → no random rolls). T4 introduces the seam now so T5 / T6 / T7 inherit it cleanly:

```python
class TickResolver:
    def resolve(
        self,
        loadout1: ShipLoadout,
        loadout2: ShipLoadout,
        *,
        pvc_damage_reduction: float = 0.0,
        guild_config: GuildConfig | None = None,
```

This is the **only** signature change T4 lands on `TickResolver.resolve`. T3's existing tests (drift-to-floor / damage helper / regen / termination) must continue to pass unchanged — none of them depend on RNG.

The nuke epicenter sample (T6 §6.2) and per-weapon-fire accuracy rolls (T5) will be the first consumers. T4 doesn't draw from the RNG; it just plumbs the parameter through.

### Categories

1. **Deterministic accuracy math — layered formula (cloak inactive).** Cover the cross-product:
   - Player vs NPC base (0.60 / 0.50).
   - Scanner: A (0 pp) / B (+5 pp) / C (+10 pp).
   - Thruster bonus: 0 pp / a moderate value (e.g. 10 pp).
   - Opponent booster debuff: 0 pp / a moderate value (e.g. 10 pp).
   - Each combination → expected `pilot_primary_acc` and `pilot_turret_acc`. Spot-check at least 4 combinations rather than exhaustively (16+ would be wasteful) — pick representatives that flex each axis independently.
2. **Cloak override.** When `opponent_cloak_active=True`, output is exactly `(clamp(cloak_set_value, ...), clamp(cloak_set_value, ...))` regardless of:
   - All scanner / thruster / booster inputs at maximum positive contribution.
   - All scanner / thruster / booster inputs at maximum negative contribution.
   - Confirms the cloak path is a REPLACE, not an additive term.
3. **Cloak override with extreme `cloak_set_value`.** Pass `cloak_set_value = 0.01` (below clamp_min 0.05) → output is `0.05` (clamp respected on the override). Pass `cloak_set_value = 1.50` (above clamp_max 0.99) → output is `0.99`. This is the Appendix B Accuracy block's clamp-applies-to-override rule.
4. **Clamp saturation.** Layered formula with all bonuses stacked (e.g. NPC base + 100 pp scanner + 100 pp thruster − 0 pp booster) → output clamps at `clamp_max` (0.99). Reverse direction (player base + 0 pp scanner + 0 pp thruster − 1000 pp booster) → output clamps at `clamp_min` (0.05).
5. **`pilot_primary_acc` vs `pilot_turret_acc` divergence.** With only the thruster term non-zero (scanner 0, booster 0, cloak inactive), `pilot_primary_acc > pilot_turret_acc`. The difference equals `own_thruster_bonus_pp / 100` (modulo clamp interaction). With cloak active, both values are equal — confirms cloak override applies to both.
6. **Thruster ramp function.** Pure-function tests:
   - `thruster_ramp(751, ...)` → `0.0` (just outside window).
   - `thruster_ramp(750, ...)` → `0.0` (at window boundary — closed interval, `<=` gate).
   - `thruster_ramp(300, ...)` → `1.0` (at floor).
   - `thruster_ramp(299, ...)` → `1.0` (below floor — clamped).
   - `thruster_ramp(525, ...)` → exactly `0.5` (midpoint check; `(750 − 525) / (750 − 300) = 225 / 450 = 0.5`).
7. **Booster debuff function.** `booster_debuff_pp(300, k_boost=0.10)` → `30.0` (Polytron at default). `booster_debuff_pp(60, k_boost=0.10)` → `6.0` (Linear). `booster_debuff_pp(0, k_boost=0.10)` → `0.0`. Returns positive magnitude.
8. **Scanner tier resolution.**

## Risk / notes

- **Cloak supersession is a REPLACE, not an additive term (§5).** Easy bug: writing `acc = base + scanner + thruster − booster − cloak_penalty`. The implementer MUST build it as a branch. The unit test for "cloak override beats all stacked positive contributions" is the canonical guard — keep it.
- **`[0.05, 0.99]` clamp applies to the cloak override too (Appendix B Accuracy block).** Don't let `CLOAK_SET_VALUE` end up below 0.05 or above 0.99 even when a guild override pushes it out of range. The cloak-active branch must `clamp(...)` its output.
- **Thruster bonus is primaries-only (§5, §7.4).** `pilot_turret_acc` MUST drop the thruster term. Rockets (T6) have their own 5% → 60% curve and do NOT use the thruster bonus either. T4 only ships `pilot_primary_acc` and `pilot_turret_acc`; the rocket curve is T6's job.
- **Booster debuff direction.** The debuff is on the **attacker's** computed accuracy. I.e., a defender's active booster reduces the *attacker's* hit chance. Sign / direction is easy to get wrong — `booster_debuff_pp(...)` returns a positive magnitude, and the layered formula in `compute_pilot_accuracy(...)` subtracts. Function naming + docstring + a directional unit test ("booster active on C2 → C1's accuracy drops, C2's unchanged" — once T8 wires this) reinforces the convention.
- **Per-weapon `accuracy_modifier` permanently DROPPED (§5).** The `SUBTYPE_ACCURACY_MOD` empty hook from T1 stays empty. T4 routes accuracy through `weapon_accuracy(pilot_acc, weapon)` which is a passthrough (Phase-1). Future homing-vs-must-aim split would land entries in `SUBTYPE_ACCURACY_MOD`. Don't preemptively populate the dict in T4.
- **Plasma scanner is a separate subclass under the same `ScannerModule` STI discriminator (§7.1).** Don't write `if has_scanner_equipped: → Tier B/C` — that incorrectly upgrades plasma-scanner-only loadouts. Discriminate by module name / subtype using the `_SCANNER_TIER_BY_NAME` mapping. Confirm the plasma scanner's exact name against seed data (`import_data/module/*.json`) at implementation time.
- **Scanner tier name-mapping is fragile.** Hard-coding four combat-scanner names is the cleanest landing for T4 given the §7.1 fixed inventory, but a future scanner addition would silently land as Tier A.
