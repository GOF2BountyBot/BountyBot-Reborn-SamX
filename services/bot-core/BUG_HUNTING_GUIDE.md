# Bug-Hunting Guide - bot-core Service

This guide defines the process for systematically verifying test correctness and fixing production code bugs discovered by the router test suite.

---

## Background

The bot-core service's shop/inventory/player/ship systems were bulk-generated by AI ~6 months ago and **never tested against real usage**. The router test suite (661 tests, 99% coverage) was written to assert **correct API contract behavior**, not to make existing code pass. However, there is a significant risk that some tests were inadvertently written to match buggy behavior rather than the correct contract. This guide defines how to audit for that.

---

## Process Overview

```
1. Audit tests for correctness    (researcher)
2. Catalog suspected bugs         (researcher)
3. Fix production code bugs       (developer)
4. Re-run and verify              (developer)
```

**All subtasks MUST be run SEQUENTIALLY - one at a time.** This helps significantly with session rate limits and ensures each step has the full context of previous steps.

---

## Phase 1: Audit Tests for Correctness

**Agent: @researcher**

For each router test file, verify that the tests assert the **correct** behavior, not just the current behavior. Specifically:

### What to check

| Check | What it means | Red flag |
|-------|---------------|----------|
| **Status codes** | Does the test assert the HTTP-correct status code? | Test asserts 200 for a create (should be 201), or 500 where 400/404 is correct |
| **Error handling** | Does the router properly re-raise HTTPExceptions? | Broad `except Exception` catching HTTPException and re-wrapping as 500 |
| **Response shape** | Does the test verify the response matches the declared schema? | Test only checks status code, not response body |
| **Service delegation** | Does the test verify correct args are passed to the service? | Test mocks return value but never asserts the mock was called correctly |
| **Validation** | Are Pydantic schema constraints actually enforced? | Test sends invalid data but doesn't verify 422 |
| **Edge cases** | What happens with None, empty list, 0, negative values? | No edge case tests exist |
| **Mock accuracy** | Does the mock return a realistic object? | Mock returns a dict where the real code expects an ORM object with attributes |

### Router priority for audit

Audit in this order (highest risk of hidden bugs first):

1. **shops.py** + `test_shops_router.py` - Transaction logic, purchase/sell flows
2. **inventory.py** + `test_inventory_router.py` - Add/remove/transfer items
3. **ships.py** + `test_ships_router.py` - Equip/unequip, loadout management
4. **players.py** + `test_players_router.py` - Credits, XP, prestige
5. **admin.py** + `test_admin_router.py` - Guild init/reset, bulk operations
6. **config.py** + `test_config_router.py` - Configuration CRUD
7. **users.py** + `test_users_router.py` - User CRUD
8. Remaining routers (data, scheduler, discord_message, about, announcements)

### Task template for @researcher

```
Read the router source file and its corresponding test file side-by-side.
For each test method, answer:

1. Is the asserted status code correct per HTTP/REST conventions?
2. Is the asserted response body correct per the Pydantic schema?
3. If the service raises ValueError, does the router return 400 or 404
   (whichever is appropriate), or does it get swallowed by a broad except?
4. If the service raises a generic Exception, does the router return 500?
5. Are there code paths in the router that have no corresponding test?
6. Does the mock setup accurately reflect what the real service returns?

Output a structured report listing:
- CORRECT: Tests that are definitely right
- SUSPECT: Tests that may be covering up bugs (explain why)
- MISSING: Code paths with no test coverage
- BUGS: Definite production code bugs found
```

## Phase 2: Catalog Suspected Bugs

**Agent: @researcher**

Consolidate findings from Phase 1 into a single bug catalog. For each entry:

```markdown
### BUG-001: [Short description]
- **File:** src/api/routers/shops.py:130
- **Test:** tests/api/test_shops_router.py::TestPurchaseItem::test_purchase_insufficient_credits
- **Symptom:** Test asserts 500 but correct behavior is 400
- **Root cause:** Broad `except Exception` on line 135 catches `ValueError` before
  the `except ValueError` on line 130 (order of except blocks is wrong)
- **Fix:** Swap the order of except blocks
- **Risk:** Low / Medium / High
- **Severity:** Bug / Enhancement / Cosmetic
```

## Phase 3: Fix Production Code Bugs

**Agent: @developer**

Work through the bug catalog from Phase 2, fixing each bug in the production code (NOT the tests). For each fix:

1. Read the router source file
2. Read the corresponding test file to understand the expected behavior
3. Fix the production code to match the correct behavior
4. Run the specific test file to verify the fix: `python -m pytest tests/api/test_X_router.py -v --tb=short`
5. Run the full suite to verify no regressions: `python -m pytest tests/api/ --tb=short -q`

### Common bug patterns to expect

| Pattern | Example | Fix |
|---------|---------|-----|
| HTTPException swallowed by broad except | `except Exception` catches `raise HTTPException(404)` | Add `except HTTPException: raise` before `except Exception` |
| Wrong status code | Router returns 200 for create (should be 201) | Add `status_code=status.HTTP_201_CREATED` |
| Variable name shadowing | `id` used instead of `player_id` (shadows builtin) | Rename variable |
| Path parameter mismatch | Route `{id}` but function param `job_id` | Align names |
| `.dict()` instead of `.model_dump()` | Pydantic v2 deprecation | Replace method call |
| Missing None check | Service returns None but router doesn't check | Add `if not result: raise HTTPException(404)` |

---

## Phase 4: Re-run and Verify

**Agent: @developer**

After all fixes:

```bash
# Full test suite
python -m pytest tests/api/ --tb=short -q

# Coverage report
python -m pytest tests/api/ --cov=api --cov-report=term-missing --no-header -q
```

Expected outcome: All tests pass (0 failures), coverage >= 99%.

## Known Bugs (Already Discovered)

These bugs were found during the initial test suite creation:

### scheduler.py - `update_job()` (line ~112)
- Uses bare `id` (Python builtin) instead of `job_id` variable
- Returns 500 because FastAPI can't serialize a builtin function

### scheduler.py - `delete_job()` (line ~122)
- Route declares path `{id}` but function parameter is `job_id`
- Every DELETE request returns 422 (FastAPI can't bind the path segment)

### health.py - Database health endpoint
- Missing null checks on `db_manager` / `schema_manager` state attributes
- Returns 500 instead of graceful degradation when managers aren't initialized

## Agent Delegation Rules

### When to use @researcher
- Reading and analyzing source code + test code side-by-side
- Identifying suspected bugs by comparing actual vs expected behavior
- Cataloging findings into structured reports
- Simple, discrete tasks that don't require writing production code

### When to use @developer
- Fixing production code bugs
- Writing new test methods for uncovered code paths
- Running tests and interpreting results
- More involved coding and analysis tasks

### When to use @general
- Highly complex or nuanced work that requires deep reasoning
- Tasks that span multiple services or require architectural decisions
- When the bug fix is non-obvious and requires understanding cross-cutting concerns

### Execution rules
- **Run all subtasks SEQUENTIALLY** - one at a time, never in parallel
- **Each subtask should be self-contained** - include all necessary context in the prompt
- **Use the todo list** to track progress through the phases
- **Mark todos complete immediately** after finishing each subtask
