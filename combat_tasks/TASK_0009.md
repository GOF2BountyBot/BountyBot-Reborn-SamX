## Deliverables

### 1. EmergencySystem (§7.7)

**Per-combatant ES state** (initialised at combatant-init):
- `consumed: bool = False`
- `invuln_remaining_ms: int = 0`

**Trigger evaluation at phase 4a** (Appendix B), AFTER all C1→C2 and C2→C1 damage has been applied (hull allowed transiently negative), processed C1 then C2:
- IF combatant has an unconsumed ES equipped AND end-of-phase `hull ≤ 0`:
  - Clamp `hull = 1` (overkill discarded; does NOT carry into invuln window).
  - `invuln_remaining_ms = EMERGENCY_SYSTEM_INVULN_S × 1000` (10 000 ms default).
  - Set `consumed = True`.
  - Emit `module_activation` event with `data = {"module": "EmergencySystem"}` — no `trigger_hp_pct` (§12 explicit: omitted for ES).

**Invuln window enforcement:**
- The phase 4 damage helper checks `invuln_remaining_ms > 0` before applying any damage to that combatant. If true, applied damage = 0.
- **Invuln-window damage event shape (locked in §12 `damage` row):** when invuln blocks incoming damage, still emit a `damage` event with `amount: 0`, `breakdown` omitted, `hp_after` unchanged, and `blocked_by: "emergency_system_invuln"`. Keeps event-source parity with non-invuln ticks (every weapon-fire hit gets a corresponding damage row) and preserves shot/hit accounting for the summary builder.

**Per-tick decrement:** at phase 1 (cooldowns) or as part of phase 4 entry, for each combatant with `invuln_remaining_ms > 0`: `invuln_remaining_ms = max(0, invuln_remaining_ms - TICK_MS)`. Pick phase 1 to colocate with cooldown decrements; document.

**Regen during invuln** (§7.7): shield + Repair Bot pulses tick normally. The dormancy rule (§3 — regen only ticks on layers below max) is unchanged. T9 just ensures the invuln gate is on the damage path, not the regen path.

**HP at expiry:** falls out naturally. With no shield and no Repair Bot → hull = 1. With Repair Bot → `1 + 10 s × repair_rate`, capped at hull max. T9 adds no special-case logic.

**Multi-source same-tick** (§7.7): ES fires ONCE at end of phase 4 regardless of how many sources contributed to the lethal damage (multiple primaries, cluster sub-munitions, nuke self-damage, mixed C1+C2 cross-fire). The evaluation is "is hull ≤ 0 right now?" — not "which hit was lethal?". Overkill is discarded.

**NOT an HP-threshold device** (§8 + §7.7): T8's phase 5 HP-threshold path must NOT include ES. ES lives strictly at phase 4a, after damage application, before display clamp.

### 2. Inert modules (§7.9 + §7.10)

The resolver MUST tolerate these in a combatant's loadout without crashing and without applying any effect:

- §7.9: GammaShield, plasma-collector turret (already inert via T7), plasma scanner (already inert via T4), JumpDrive (Khador), TimeExtender (Rhoda Vortex), Compressor, MiningDrill, TractorBeam, Cabin, Signature, SpectralFilter.
- §7.10 Phase-2 deferred (NEVER activate in Phase-1): ShieldInjector (Phoenix SIS), RepairBeam, TransfusionBeam.

**Phase-1 implementation:** explicit no-op. The module dispatcher recognizes these classes and skips them — no cooldown ticking, no event emission, no state mutation. Recommended: do NOT include them in the combatant module-state at all (filter at loadout-ingest), to keep per-tick iteration tight. Implementer's choice; either is acceptable provided the no-op contract holds.

Loadout building is out of scope (§10 loadout contract). T9 only guarantees the resolver does not break on their presence.

**Phase-ordering enforcement** (Appendix B): events within a tick are emitted in strict phase order — `1 cooldowns → 2 regen → 3 fire eval → 4 damage → 4a ES module_activation → 4b clamp → 5 HP-threshold module_activation → 6 distance → 7 (no-op) → 8 termination`. Within each phase, C1 before C2.

**Phase 7 ("Emit timeline events")** in Appendix B is a no-op for the chosen inline-emission model. Document this explicitly: events are appended to the timeline list as they occur within each phase, not buffered and flushed at phase 7. Phase 7 in code is a comment marker only.

**ES emission ordering:** the ES `module_activation` event MUST emit at phase 4a — AFTER all `damage` events for that tick (including any zero-applied invuln events) and BEFORE any phase 5 HP-threshold `module_activation` events.

### 4. Per-combatant summary builder (§12 `data.summary`)

After fight termination (phase 8 of the terminal tick), build the summary dict per §12's JSONC shape:

```
{
  "outcome": "win" | "stalemate",
  "reason":  "hp_depleted" | "time_cap" | "mutual" | "draw",
  "duration_ticks": int,
  "winner": str | None,             # None on stalemate
  "combatants": {
    "1": { ...per-combatant... },
    "2": { ...per-combatant... }
  }
}
```

Per-combatant block:

| Field | Source |
|---|---|
| `name`, `ship` | combatant identity (captured at `fight_start`) |
| `start_hp: {shield, armour, hull}` | `fight_start` event payload |
| `final_hp: {shield, armour, hull}` | `fight_end` event payload (POST-clamp values) |
| `damage_dealt` | sum of post-clamp HP absorbed by opponent from this combatant's actions |
| `damage_taken` | sum of post-clamp HP absorbed on this combatant from opponent's actions |
| `shots_fired` | count of `weapon_fire` events with `actor == this combatant` |
| `shots_hit` | count of `weapon_fire` events with `actor == this combatant` AND `data.hit == True` |
| `accuracy` | `shots_hit / shots_fired`, 0.0 if `shots_fired == 0` |
| `module_activations` | dict counting discrete activations: `{"cloak": N, "booster": M, "emergency_system": P}` (keys present only for activations that fired ≥ 1 time, OR all three keys always present at 0 — pick one and document; recommend always-present-at-0 for stable downstream parsing) |
| `secondary_fired` | dict counting secondaries by subtype: `{"rocket": X, "missile": Y, "cluster-missile": Z, "nuke": W, "shock-blast": V}` (same always-present-vs-sparse choice — match `module_activations`) |

**Activation key naming (locked):** lowercase_snake_case — `{"cloak": N, "booster": M, "emergency_system": P}` — per §0.3 and the now-updated §12 example. Same convention applies to the `module_activation` event's `module` field. Friendly-name rendering (`"Cloak"`, `"Booster"`, etc.) happens at the embed/visualization layer, deferred post-Phase-1.

**Cluster missile `damage_dealt` semantics** (§6.2 + §12): the `total_damage` field on a cluster `weapon_fire` event reports the weapon's swung output (`K × damage_per_submunition`). The summary's `damage_dealt` aggregates **post-clamp absorbed damage**, which can be lower than swung when overkill occurs. Source `damage_dealt` from `damage` events (post-clamp `amount`), NOT from `weapon_fire.data.total_damage`. ES-blocked invuln events contribute 0.

**Passive modules NOT counted** (§13): Repair Bot, Thruster, PrimaryWeaponMod, shield regen → no `module_activation` event → no summary entry. Only cloak / booster / ES count.

**`FightResults` population:**
- `FightResults.combat_log: list[dict]` ← the full timeline (list of `CombatEvent` dicts, in emission order).
- `FightResults.metadata: dict` ← the full envelope:
  ```
  {
    "schema_version": 1,
    "summary": { ...as above... },
    "metadata": {
      "tick_ms": TICK_MS,
      "total_ticks": <terminal tick>,
      "resolver": "tick_v1",
      "pvc_damage_reduction": <float from resolver input>
    }
  }
  ```
- Note: §12's JSONC blob shows `timeline` as a sibling of `summary` inside the persisted `data` blob. In memory, the timeline lives on `FightResults.combat_log` (separate from `.metadata`) — T10 stitches them into the `data` JSON at persist time. T9 produces both halves; T10 assembles.
- `metadata.pvc_damage_reduction`: populate from the `pvc_damage_reduction` argument the resolver received (set by callers — `0.33` in PvC, `0.0` in PvP/preflight). T9 just passes through whatever T3 + T5/T6 plumbed.

## Test surface (≤ 2 mocks per test; prefer real objects)

**EmergencySystem:**
- Single lethal hit: hull = 50, takes 200 damage → ES fires, hull = 1, invuln_remaining_ms = 10 000.
- Multi-source same tick: C1 fires 2 primaries + 1 missile, all land on C2, total > C2 hull → ES fires ONCE; one `module_activation` event.
- Cluster overkill: 5-sub-munition cluster, total damage = 5× lethal → ES fires once; hull = 1; overkill discarded; subsequent ticks regen from 1.
- Nuke self-damage: firer's own nuke self-damage reduces firer hull ≤ 0 → firer's ES fires (self-damage is a damage source per §3 + §7.7).
- Invuln blocks all incoming damage: during 10 s window, every damage attempt → `amount: 0`, `blocked_by: "emergency_system_invuln"` annotation on the event.
- Regen continues during invuln: shield pulse + Repair Bot pulse fire normally inside the window.
- HP at expiry — no regen: hull = 1 at window end.
- HP at expiry — with Repair Bot: hull ≈ `1 + 10 × rate`, capped at max.
- Consumable: ES fires once, second equipped ES instance (malformed loadout) is ignored after consumption. Flagged as defensive guard — undefined per §10 loadout contract but resolver must not crash.
- Not a threshold device: HP-percent crosses 33 % but hull > 0 → ES does NOT fire (phase 5 path never touches ES).

**Inert modules:**
- Combatant equipped with GammaShield + RepairBeam → no events, no state mutations, no errors over a full sim.
- All §7.9 + §7.10 modules in the same loadout → same: no-op, no crash.

**Timeline ordering:**
- Tick with regen + primary fire + damage + booster activation → events emit in `[regen, weapon_fire, damage, module_activation]` order.
- Same tick both combatants regen → C1's `regen` event precedes C2's.

## Risks & notes

- **ES is NOT an HP-threshold device** (§8). Easy mistake: bolting ES onto T8's phase 5 path. ES lives at phase 4a — AFTER damage, BEFORE display clamp. Phase 5 must remain cloak + booster only.
- **End-of-phase hull check, not per-event** (§7.7): do not try to identify "the lethal hit." Apply all phase 4 damage first, then check `hull ≤ 0` once per combatant.
- **Invuln + damage events**: locked choice is to emit `damage` with `amount: 0` + `blocked_by: "emergency_system_invuln"`. Keeps shot/hit accounting honest. Document at the call site.
- **Passive modules NOT in `module_activations`** (§12 + §13): Repair Bot, Thruster, PrimaryWeaponMod, shield regen never produce `module_activation` events. Only cloak / booster / ES are counted.
- **Cluster `total_damage` vs `damage_dealt`**: easy conflation. `total_damage` on `weapon_fire` is swung output; `damage_dealt` on the summary is post-clamp absorbed. Source `damage_dealt` from `damage` events, not `weapon_fire` events.
- **Multi-instance defensive guard**: §10 loadout contract says builder owns uniqueness. If a malformed loadout has multiple ES instances, resolver consumes the first and ignores the rest. Don't crash; don't fire twice.
- **`fight_end.final_hp` POST-clamp**: phase 8 reads HP after phase 4b clamp. Verify; do not leak transient negative values into the summary or the `fight_end` event.
- **`module_activation` payload shape**: cloak/booster carry `trigger_hp_pct` (T8); ES omits it (§12 explicit). Don't add `trigger_hp_pct: null` for ES — omit the key entirely.
- **`metadata.pvc_damage_reduction`**: T9 just plumbs through what the resolver received from T3/T5/T6. The proper wire-up (callers passing the value via the new `pvc_damage_reduction` arg) lands in T10. For T9 tests, use whatever value the existing resolver entry point exposes (likely 0.0 in PvP).
- **Spec ambiguity — activation key casing**: §12 example shows `"Cloak"` / `"Booster"` capitalized. Naming convention §0.3 + secondary subtype precedent (`"rocket"`, `"cluster-missile"`) argue for lowercase. Recommending lowercase snake_case (`cloak`, `booster`, `emergency_system`); flagging for spec-author confirmation before merge.
- **Spec ambiguity — sparse vs always-present summary keys**: §12 example shows only fired modules / subtypes as keys. Recommending always-present-at-0 for `module_activations` (cloak/booster/emergency_system) and `secondary_fired` (rocket/missile/cluster-missile/nuke/shock-blast) for stable downstream parsing. Flagging for spec-author confirmation.
- **Cross-task verification**: per-task grep audit (not full reads) is sufficient to verify §12 event-vocabulary coverage and `data.cause` consistency. If a gap is found, surface in the PR description — do not silently retroactively edit T3/T5/T6/T7/T8 emission sites without calling it out.
