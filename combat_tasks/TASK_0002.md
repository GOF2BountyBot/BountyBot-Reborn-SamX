### D8. `CombatLogRepository`

**File:** `services/bot-core/src/persist/repositories/combat_log_repository.py` (new)

CRUD-only skeleton, mirroring `DuelRepository`'s pattern:

```python
class CombatLogRepository(IRepository[CombatLog]):
    async def add(self, db: AsyncSession, obj: CombatLog, *, commit: bool = True) -> CombatLog: ...
    async def get_by_id(self, db: AsyncSession, obj_id: int) -> CombatLog | None: ...
    async def list_for_player(self, db: AsyncSession, user_id: int, limit: int = 20) -> list[CombatLog]: ...
    async def delete_older_than(self, db: AsyncSession, cutoff: datetime, *, commit: bool = True) -> int: ...

    # IRepository abstract stubs that don't apply:
    async def get_by_name(...): raise NotImplementedError("combat_log is not queried by name")
    async def list_all(...): ...  # implement; trivial select
    async def remove(...): ...    # implement; standard delete pattern
    async def create_or_update(...): raise NotImplementedError("combat_log rows are immutable post-insert")
```

- `list_for_player(user_id, limit)` runs the §12 canonical query: `WHERE combatant1_user_id = :uid OR combatant2_user_id = :uid ORDER BY created_at DESC LIMIT :n`.
- `delete_older_than(cutoff)` returns the deleted row count (`int`), mirroring `BountyRepository.delete_terminal_older_than` / `DuelRepository.delete_terminal_older_than`. **T10** will call this from `db_retention_executor`; T2 only lands the method.
- All write methods use `try/except` with `await db.rollback()` on failure per `/proj/AGENTS.md`.
- **NPC invariant enforcement** (§12): inside `add()`, before `db.add(obj)`, assert `obj.combatant1_user_id is not None or obj.combatant2_user_id is not None` and raise `ValueError` if both are NULL. Repository-level enforcement is the recommended path — see Risks.

## Risks & notes

- **`manual_turret_mode` storage choice — dedicated column vs JSON blob.** §6.3 leaves this to the implementer. Trade-off:
  - *Dedicated `Boolean` column* — queryable (`WHERE manual_turret_mode = true`), idiomatic with the rest of `PlayerShip`'s scalar columns (`is_active`, `nickname`), trivial Alembic add. **Recommended.**
  - *JSON-blob key* — the existing JSON columns on `PlayerShip` are typed `list[str] | None`, not free-form dicts; using one would require a new JSON `settings` column anyway, which is strictly worse than a typed Boolean.
- **NPC invariant — repository, not DB CHECK.** §12 says "the persist layer may assert this." A `ValueError` in `add()` is simpler, matches the project's existing repository-layer validation style, and avoids a Postgres-specific CHECK constraint that complicates downgrade. Document in the repo method's docstring; T10's `CombatLogService.persist()` will rely on this guard.
- **`data` column is generic `JSON`, not `JSONB`.** §12 explicitly notes the blob is "never queried internally" and the existing convention uses generic `JSON` (e.g. `Ship.extra_atts` from revision 0009, `PlayerShip.weapons`). Do not opportunistically upgrade to `JSONB` "in case we want to query later" — that's a future task's call.
- **`created_at` is the retention key.** Must be `DateTime(timezone=True)` with `default=lambda: datetime.now(UTC)`. Do NOT use `server_default=func.now()` here — the existing model convention (see `PlayerShip.created_at`, `DuelRequest.created_at`) is application-side default for UTC consistency.
- **Revision numbering.** The `versions/` directory already contains `0010_commodity_schema.py` and an auto-generated `6510020b3335_auto_feat_promote_demote_flow_.py`. The implementer MUST run `alembic heads` (or `python -m persist.database.run_migration current` against a fresh DB after `upgrade head`) to identify the true tip before writing `down_revision`. Pick the next sequential slot (likely `0011_*`).
- **Idempotent migration pattern.** Mirror `0009`'s `inspector.get_columns()` / `inspector.get_indexes()` checks so fresh installs (where revision `0001` builds tables from current ORM metadata) are no-ops, while existing prod DBs get the additive changes. This is also why `downgrade()` should guard each `op.drop_column` / `op.drop_index` with an existence check.
- **`schema_version: 1` in `data` blob.** §12 stamps `data.summary.schema_version: 1`. That value is written by the *service* (T10), not by the repository or migration; T2 needs no schema-version handling.
- **List-typed `GuildConfig` columns.** Two Appendix A constants are int-lists: `CLOAK_HP_THRESHOLDS_PCT = [66, 33]` and `BOOSTER_HP_THRESHOLDS_PCT = [80, 60, 40, 20]`. Store these as `String` (comma-separated, mirroring the env-var format from T1's `_track_int_list` helper). `resolve_constant()` will need a list-aware variant (or the call-sites parse the string themselves) — flag for the implementer to decide; either path is acceptable. The other 24 constants are scalars and need no special handling.
- **`context` enum validation lives at the service layer.** §12 declares the column as `String(20)`; T10's `CombatLogService.persist()` (and `fight_ships(context=...)` boundary) enforces the three-value enum. T2 stores plain VARCHAR with no DB-level constraint — consistent with existing project style (no DB enum types).
