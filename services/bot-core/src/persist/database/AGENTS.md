## Overview

This directory contains the database infrastructure:

| File | Purpose |
|---|---|
| `manager.py` | `DatabaseManager` singleton — async engine, session factory, health checks |
| `migration_manager.py` | `MigrationManager` — Alembic wrapper for zero-friction migrations |
| `tablenames.py` | `TableNames` enum — single source of truth for all table names |
| `run_migration.py` | CLI tool for running Alembic commands manually |
| `alembic.ini` | Alembic configuration file |
| `revisions/` | Alembic `env.py` + `script.py.mako` + `versions/` migration scripts |

`SchemaManager` lives in the sibling package `persist/schemas/schema_manager.py`
(not in this directory) — see its section below.

## DatabaseManager (`manager.py`)

The module exposes a singleton instance:

```python
from persist.database.manager import db_manager, get_db_session
```

### Lifecycle

```python
# Startup (called in main.py lifespan):
await db_manager.initialize()

# Shutdown (called in main.py lifespan; the method is async):
await db_manager.shutdown()
```

`initialize()` creates:
1. An `AsyncEngine` via `create_async_engine()` (asyncpg dialect), with
   orjson as `json_serializer`/`json_deserializer` for all JSON/JSONB columns
   (P4-T2; `OPT_NAIVE_UTC`, no `OPT_NON_STR_KEYS` — int-keyed writes fail fast)
2. A `sessionmaker(bind=engine, class_=AsyncSession, expire_on_commit=False)`
3. Connection pool with env-var-configurable settings

### Getting a Session

```python
# In routers:
from persist.database.manager import get_db_session

async with get_db_session() as db:
    result = await my_repo.get_by_id(db, item_id)

# In executors:
async with db_manager.get_session() as db:
    result = await my_repo.list_all(db)
```

Both are equivalent — `get_db_session()` is a module-level convenience function
that returns `db_manager.get_session()`.

`get_session()` rolls back on exception, and on clean exit **auto-commits any
pending transaction** (AC-7 / B.34 defense-in-depth layer 3 — see
`persist/repositories/AGENTS.md`). Callers that mutated ORM instances and do
NOT want them persisted must call `await session.rollback()` before exiting.

### Connection URL

```
postgresql+asyncpg://{POSTGRES_USER}:{POSTGRES_PASSWORD}@{POSTGRES_HOST}:{POSTGRES_PORT}/{POSTGRES_DB}
```

Defaults: `bounty/bounty@bounty_db:5432/bountydb`

### Connection Pool Configuration

| Env Var | Default | Purpose |
|---|---|---|
| `DB_POOL_SIZE` | `40` | Base connection pool size |
| `DB_MAX_OVERFLOW` | `20` | Additional connections above pool_size |
| `DB_POOL_TIMEOUT` | `30` | Seconds to wait for a connection |
| `DB_POOL_RECYCLE` | `3600` | Seconds before recycling a connection |
| `DB_ECHO` | `false` | Log all SQL to stdout |

`pool_pre_ping=True` is always enabled — SQLAlchemy sends a lightweight ping before using a connection to detect stale connections.

Pool sizing is guarded against the Postgres `max_connections` ceiling (100 on
this deployment): `_load_config()` raises `ValueError` if
`pool_size + max_overflow >= 100` and logs a warning above 75% of the ceiling.
Sizing rationale (Decision D10, single uvicorn worker):
`pool_size + max_overflow >= (2 × AUTOCOMPLETE_WARM_CONCURRENCY) + live_headroom`.

### Health Check

```python
health_info = await db_manager.get_health_info()
# Returns: {"status": str, "connection_pool": dict, "connectivity": bool, "error": str | None}
# connection_pool: {"size", "checked_in", "checked_out", "overflow", "status"}
```

Used by the health router (`api/routers/health.py`).

## MigrationManager (`migration_manager.py`)

Wraps Alembic to provide the single migration control point. **This is the only way migrations should be run** — never call Alembic directly.

### Factory Methods

```python
# From an asyncpg URL (converts automatically):
mgr = MigrationManager.from_async_url(db_manager._connection_string)

# From environment variables:
mgr = MigrationManager.from_env()
```

`from_async_url()` converts `postgresql+asyncpg://...` → `postgresql://...` (psycopg2 sync URL required by Alembic).

### Key Methods

| Method | Purpose |
|---|---|
| `ensure_current()` | Apply all pending migrations (`upgrade head`); **called on every startup** in `main.py`; retries `get_current_revision()` up to 5× on `OperationalError` |
| `auto_generate(message)` | Generate a new autogenerated revision file |
| `detect_pending()` | Return list of unapplied revision IDs (empty = at head) |
| `get_current_revision()` | Current DB revision from `alembic_version` (or `None` if unversioned) |
| `get_head_revision()` | Head revision ID from the script directory (or `None`) |
| `downgrade(target="-1")` | Roll back to target (`"-1"` = one step, `"base"` = all) |
| `history()` | Return migration history as a `list[str]` of formatted lines |

### Startup Usage (in main.py)

```python
migration_mgr = MigrationManager.from_async_url(db_manager._connection_string)
migration_mgr.ensure_current()  # Blocks startup if migration fails
```

## SchemaManager (`persist/schemas/schema_manager.py`)

Lives in `persist/schemas/` (NOT in this directory). Reads the `schema` table
(mapped to the `SchemaVersion` model — PK is `version`, plus `applied_at` and
`description`) to provide version metadata for health-check endpoints. It is
**informational only** — it does not apply or control migrations.
`CURRENT_SCHEMA_VERSION = "1.0.0"` is a module constant.

```python
from persist.schemas.schema_manager import initialize_schema

schema_manager = await initialize_schema(db_manager)
app.state.schema_manager = schema_manager

# Later in health router:
health_info = await schema_manager.get_schema_health_info()
# Returns: {"version": str | None, "expected_version": str, "version_match": bool}
# (or {"status": "error", "error": str} on failure)
```

`initialize_database(run_create_all=False)` retains a deprecated
`create_all()` path used **only** by SQLite-based tests; production DDL is
Alembic's job.

## run_migration.py CLI

Manual Alembic operations from inside the container:

```bash
# From inside the bot-core container:
cd /app/src

# Apply all pending migrations:
python -m persist.database.run_migration upgrade

# Roll back one migration (target is a --target flag, NOT positional):
python -m persist.database.run_migration downgrade --target -1

# Roll back to a specific revision:
python -m persist.database.run_migration downgrade --target abc123

# Check current revision:
python -m persist.database.run_migration current

# View migration history:
python -m persist.database.run_migration history

# Generate a new autogenerated revision:
python -m persist.database.run_migration revision -m "add new_field to player"
```

Actions map onto `MigrationManager`: `upgrade` (with default `--target head`)
calls `ensure_current()`, `revision` calls `auto_generate(message)`,
`downgrade` calls `downgrade(target)`, `history` calls `history()`; `current`
shells out to `alembic.command.current`.

## Alembic Configuration (`alembic.ini` + `revisions/`)

- `alembic.ini` — Alembic config; `script_location = %(here)s/revisions`
- `revisions/env.py` — Alembic env script; imports all models via `from persist.models import *` (which triggers the package's `pkgutil.walk_packages` auto-import), sets target metadata to `Base.metadata`
- `revisions/versions/` — Individual migration scripts

**Important**: `revisions/env.py` must import all ORM models before `Base.metadata` is passed to Alembic. This is achieved by the `from persist.models import *` wildcard import.

## How to Create a New Migration

1. **Modify your model** in `persist/models/<name>.py` (add/change/remove columns)

2. **Generate the revision** (inside the bot-core container):
   ```bash
   cd /app/src
   python -m persist.database.run_migration revision -m "describe the change"
   ```
   This creates a new file in `revisions/versions/` with `upgrade()` and `downgrade()` functions.

3. **Review the generated file** — autogenerate is not perfect; always inspect:
   - Check that column types match your intent
   - Ensure nullable constraints are correct
   - Verify foreign key constraints
   - Add any missing `op.create_index()` or `op.drop_index()` calls

4. **Apply the migration**:
   ```bash
   python -m persist.database.run_migration upgrade
   ```

5. **Commit the migration file** — it lives in `revisions/versions/` and must be committed to source control.

## Migration Notes

- **Revision 0001** creates all tables from current ORM metadata. This is a "moving target" revision — it reflects the current state of models at the time it was generated. This is intentional for fresh installs.
- **Future schema changes** MUST use `run_migration revision -m "describe change"` to generate proper `op.add_column()` / `op.drop_column()` / etc. migrations. Do NOT modify revision 0001.
- **NOT NULL columns** on existing tables require `server_default` in the migration for existing rows. Example:

```python
# Example migration adding a NOT NULL column to an existing table
from alembic import op
import sqlalchemy as sa

def upgrade():
    op.add_column('players', sa.Column(
        'new_field',
        sa.String(50),
        nullable=False,
        server_default='default_value'
    ))

def downgrade():
    op.drop_column('players', 'new_field')
```

- `compare_server_default=True` and `compare_type=True` are set in `env.py`, so Alembic will detect server-default and column-type changes during autogeneration.

---

## Migration Anti-Patterns

- **Never use `Base.metadata.create_all()`** — this was the legacy approach and bypasses Alembic's revision tracking
- **Never manually edit the `schema` table** — let MigrationManager manage it
- **Never skip the review step** — autogenerate misses some changes (e.g., PostgreSQL ARRAY type changes, enum alterations)
- **Never delete migration files** — even old ones must stay for `downgrade` to work

## Connection URL Conversion

`MigrationManager` handles the asyncpg → psycopg2 URL conversion internally. If you ever need to do this manually:

```python
# asyncpg URL (for SQLAlchemy async):
async_url = "postgresql+asyncpg://user:pass@host:5432/db"

# psycopg2 URL (for Alembic, synchronous):
sync_url = async_url.replace("postgresql+asyncpg://", "postgresql://")
```

This is encapsulated in `MigrationManager.from_async_url()` — always prefer that factory method.
