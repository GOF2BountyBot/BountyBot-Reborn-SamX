# T11 — Item-detail embed enrichment (§14)

Surface mechanically-relevant weapon/module attributes (EMP damage, cluster burst count, nuke effective magnitude + self-damage warning, PrimaryWeaponMod per-shot breakdown) as explicit Pydantic response fields on bot-core item schemas and render them on the discord-gateway item-detail embeds. Rendering-only — no resolver coupling.

## Spec references

- **§14** — required embed fields (the four bullets); §14 is the only mechanic-bearing section T11 implements.
- **§4** — Phase-1 pure-EMP inventory (Luna/Sol/Dia EMP primaries, Mamba EMP missile, Netha EMP mine).
- **§6.2** — cluster missile `burst_count`; nuke `magnitude_m` + falloff formula.
- **§7.8** — PrimaryWeaponMod (`damage_pct`, `fire_rate_pct`, legacy `dpsMultiplier`). Kept on seed for embed display and the current SimpleTTKResolver.
- **Appendix A** — `NUKE_MAGNITUDE_SCALE` (default 0.10), `NUKE_FRIENDLY_FACTOR` (default 0.25).

## Entry conditions

- Independent of T1–T10. T11 consumes no resolver runtime state; can land at any point per `/proj/TODO.md` line 117.
- All four §14 attribute families already exist in seed data (`/proj/services/bot-core/import_data/`); seed-fix `e87db57` corrected EMP-blasters, `burst_count` and `magnitude_m` are present on existing cluster/nuke definitions. T11 only closes the schema/embed gap.
- Item-detail Pydantic surface today lives in `services/bot-core/src/api/schemas/about_schema.py` (`ItemResponse` + subclasses `ModuleResponse`, `WeaponResponse`, `PrimaryWeaponResponse`, `SecondaryWeaponResponse`, `TurretWeaponResponse`). `extra_atts: dict[str, Any] | None` lives on `ItemResponse`.
- Cog item-detail rendering today lives in `services/discord-gateway/src/cogs/inventoryCog.py` (and `shipsCog.py` for ship-mounted weapons). Embeds are built with `discord.Embed` + `add_field` directly.

## Deliverables

### (1) bot-core schema enrichment

`services/bot-core/src/api/schemas/about_schema.py` (or whichever item-detail schema modules currently exist — verify at implementation time):

- Keep `extra_atts` intact on `ItemResponse` for backward compatibility.
- Add explicit response fields, each `| None` defaulted to `None`, populated by the router/service layer from `extra_atts` + computed values:

  On `WeaponResponse` (or its subclasses where applicable):
  - `emp_damage: int | None` — surfaced from `extra_atts["emp_damage"]` when present. Applies to any weapon with EMP capability (primary, secondary, mine).
  - `burst_count: int | None` — surfaced from `extra_atts["burst_count"]` when present. Applies to cluster missiles (and any future burst weapons).
  - `nuke_direct_damage: int | None` — equal to `damage` when `subtype == "nuke"`.
  - `nuke_effective_magnitude_m: int | None` — = `magnitude_m × NUKE_MAGNITUDE_SCALE`, rounded to int. Computed in the schema/service layer using the global default from `GameConstants`.
  - `nuke_self_damage_factor: float | None` — equal to `NUKE_FRIENDLY_FACTOR` when `subtype == "nuke"`.

  On `ModuleResponse`:
  - `damage_pct: int | None` — surfaced from `extra_atts["damage_pct"]` when the module is a `PrimaryWeaponModModule`.
  - `fire_rate_pct: int | None` — from `extra_atts["fire_rate_pct"]`.
  - `dps_multiplier: float | None` — from `extra_atts["dpsMultiplier"]`. Note: seed key is camelCase (`dpsMultiplier`); schema field is snake_case (`dps_multiplier`) per project Pydantic convention.

- Use `model_config = ConfigDict(from_attributes=True)` (verify it's set on the base or each subclass). Do NOT use deprecated `class Config` or `.dict()`.
- Population path: either compute in the router/service when assembling the response, or expose computed properties on the response model — pick whichever matches the existing pattern in `about_schema.py`. Do not push computation into ORM models.

### (2) discord-gateway cog rendering

For each cog path that renders an item-detail embed (start with `inventoryCog.py`; check `shipsCog.py` for ship-mounted item display; check for shared embed helpers under `services/discord-gateway/src/utils/`):

- When `emp_damage` is non-null and > 0: render a distinct field labelled **"EMP damage"** alongside (or in place of) the existing damage field. For EMP-blaster primaries (`damage_per_shot: 0`), this prevents the misleading "Damage: 0" display.
- When `burst_count` is non-null: render two fields — **"Burst count"** (the value) and **"Total damage on full hit"** (= `burst_count × damage`). Place adjacent to the per-shot damage field so per-sub-munition vs total is unambiguous.
- When `nuke_effective_magnitude_m` is non-null: render
  - **"Direct hit damage"** (= `nuke_direct_damage`),
  - **"Effective blast radius"** (= `nuke_effective_magnitude_m`, NOT raw `magnitude_m`),
  - a self-damage warning field/text computed as `direct_hit × nuke_self_damage_factor` at point-blank — example label: **"Self-damage at point-blank"** with value `~<N> hp`.
- When `dps_multiplier` is non-null (PrimaryWeaponMod path): render three fields — **"Damage modifier"** (`damage_pct`), **"Fire rate modifier"** (`fire_rate_pct`), **"Net DPS shift"** (`dps_multiplier`). All three; do not collapse to just `dps_multiplier`.
- Labels above are the recommended phrasing per §14; final wording is up to the implementer as long as physical/EMP and raw/effective distinctions are unambiguous.
- Items without any of these attributes render unchanged.

## Test surface

Max 2 mocks per test (per `/proj/AGENTS.md`).

### bot-core schema field exposure

- `emp_damage` is non-null and matches seed for Luna EMP (3), Sol EMP (5), Dia EMP (8), Mamba EMP missile, Netha EMP mine; null for non-EMP weapons.
- `burst_count` is non-null and matches seed for Shesha (3), Garuda-IV (4), Patala (5); null for non-cluster weapons.
- `nuke_effective_magnitude_m` is correctly computed for representative nukes (e.g. Liberator: `magnitude_m × 0.10`, Extinctor: same formula). Use the current seed magnitude — do not hard-code expected raw values without reading the seed.

- `extra_atts` blob remains present on responses (backward-compat regression check).

### discord-gateway embed rendering

- EMP-blaster embed contains a field whose name matches `EMP damage` (case-insensitive) AND does not display a misleading bare "Damage: 0".
- Cluster missile embed contains `burst_count` and `total damage on full hit` fields with the correct derived value.
- Nuke embed contains `direct hit damage`, `effective blast radius`, and a self-damage warning field; does NOT display raw `magnitude_m`.
- PrimaryWeaponMod embed contains all three fields (`damage_pct`, `fire_rate_pct`, `dps_multiplier` labelled as net DPS shift). Nirai Overdrive and Nirai Overcharge produce different field values despite identical `dps_multiplier`.
- Non-affected items (e.g. a plain Nirai pulse primary, a Scanner module) render with no new fields.

## Risk / notes

- §14 is the only spec section T11 implements. Do not fish in §6.2 / §7.8 for combat mechanics — T11 is rendering-only.
- **`NUKE_MAGNITUDE_SCALE` — global only for the embed (locked):** schema computes effective magnitude using the global `GameConstants.NUKE_MAGNITUDE_SCALE`. Per-guild overrides still apply at fight-time; the embed shows the default-world view. If per-guild embed rendering becomes a real ask, future plumbing lands in a follow-up task.
- **Seed key casing**: `extra_atts["dpsMultiplier"]` is camelCase in seed; schema field is `dps_multiplier` (snake_case). Don't confuse the source lookup with the response field name.
- **`NUKE_FRIENDLY_FACTOR` is identical across all nukes** (Appendix A default 0.25). Do not try to read it per-nuke from seed.
- **Backward compat with `extra_atts`**: existing callers may still read the blob. Keep it; T11 only ADDS explicit fields.
- **§14 motivation is visibility, not redesign**: do not refactor the embed layout. Add the missing fields in the existing structure.
- **Phase-2 deferred subtypes**: `emp-bomb`, `ionizing-missile`, sentry-gun etc. are NOT in T11 scope. Mamba EMP (in scope per §4) and Netha EMP (mine — already in seed via fix `e87db57`) ARE in scope for the `emp_damage` label path because both are equippable/inspectable from inventory.
- **No resolver coupling**: T11 must not import from any resolver module. It reads only seed data via existing repositories and surfaces values in Pydantic + Discord embed layers.
- **Cog test pattern**: existing cog tests construct real `discord.Embed` and inspect `embed.fields`. Mock the API client; do not mock Discord itself. Grep `services/discord-gateway/tests/cogs/` for `add_field` / `Embed` to find the pattern.
- **PR shape**: bot-core schema change and gateway cog change are tightly coupled (gateway depends on schema). Recommend ONE bundled PR. The spec author can override if separate PRs are preferred.
